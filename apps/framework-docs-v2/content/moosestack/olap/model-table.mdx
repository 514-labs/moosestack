# Olap Table

Use `OlapTable` to define a typed ClickHouse table to be managed in code. The model type becomes the table schema, and the table object becomes the resource you query, insert into, use as a stream destination, or target from materialized views.

Use this page to look up constructor syntax, config fields, default behavior, and engine-specific options for `OlapTable`.

<Callout type="info" title="Enable OLAP before defining tables">
Turn on `features.olap` in `moose.config.toml` before creating OLAP tables.
</Callout>

## Basic usage

Use the simplest constructor when the default `MergeTree` engine and inferred primary key are enough.

<LanguageTabs>
  <LanguageTabContent value="typescript">
```ts filename="app/table.ts" copy
import { OlapTable } from "@514labs/moose-lib";

interface Record {
  id: string;
  name: string;
  timestamp: Date;
}

export const table = new OlapTable<Record>("table");
```
  </LanguageTabContent>
  <LanguageTabContent value="python">
```py filename="app/table.py" copy
from datetime import datetime

from moose_lib import OlapTable
from pydantic import BaseModel

class Record(BaseModel):
    id: str
    name: str
    timestamp: datetime

table = OlapTable[Record]("table")
```
  </LanguageTabContent>
</LanguageTabs>

`Key` in TypeScript and `Key[...]` in Python mark fields Moose should use for inferred primary-key generation unless you override that behavior with `primaryKeyExpression` or `primary_key_expression`.

<Callout type="warning" title="Plan ORDER BY before you create the table">
ClickHouse cannot change `ORDER BY` in place. Choose `orderByFields` or `order_by_fields` from real filter patterns before you create the table, and place lower-cardinality columns before higher-cardinality ones for better pruning.
</Callout>

<Callout type="info" title="Start without partitioning unless you need lifecycle management">
Use `partitionBy` or `partition_by` when you need retention, archival, or other data-lifecycle operations. If you do not have a clear lifecycle need yet, start without partitioning.
</Callout>

## Common configuration

Use table config when you need to control ordering, versioning, partitioning, lifecycle behavior, or a non-default engine.

<LanguageTabs>
  <LanguageTabContent value="typescript">
```ts filename="app/table.ts" copy
import {
  ClickHouseEngines,
  LifeCycle,
  OlapTable,
} from "@514labs/moose-lib";

interface EventRecord {
  id: string;
  userId: string;
  timestamp: Date;
  updatedAt: Date;
}

export const events = new OlapTable<EventRecord>("events", {
  engine: ClickHouseEngines.ReplacingMergeTree,
  orderByFields: ["userId", "timestamp", "id"],
  partitionBy: "toYYYYMM(timestamp)",
  ver: "updatedAt",
  version: "1.0",
  lifeCycle: LifeCycle.FULLY_MANAGED,
});
```
  </LanguageTabContent>
  <LanguageTabContent value="python">
```py filename="app/table.py" copy
from datetime import datetime

from moose_lib import LifeCycle, OlapConfig, OlapTable, ReplacingMergeTreeEngine
from pydantic import BaseModel

class EventRecord(BaseModel):
    id: str
    user_id: str
    timestamp: datetime
    updated_at: datetime

events = OlapTable[EventRecord]("events", config=OlapConfig(
    engine=ReplacingMergeTreeEngine(ver="updated_at"),
    order_by_fields=["user_id", "timestamp", "id"],
    partition_by="toYYYYMM(timestamp)",
    version="1.0",
    life_cycle=LifeCycle.FULLY_MANAGED,
))
```
<Callout type="info" title="Python engine config classes are preferred">
Use engine config classes such as `MergeTreeEngine()` or `ReplacingMergeTreeEngine(...)` in Python. The `ClickHouseEngines` enum still works for backward compatibility, but it emits a deprecation warning.
</Callout>

  </LanguageTabContent>
</LanguageTabs>

## Engine-specific options

Use these fields only when the selected engine supports them.

| Engine | Extra fields | Use it when |
| --- | --- | --- |
| `MergeTree` / `MergeTreeEngine()` | None | You want the default append-oriented engine. |
| `ReplacingMergeTree` / `ReplacingMergeTreeEngine(...)` | `ver`, `isDeleted` in TypeScript; `ver`, `is_deleted` in Python | Later rows should replace earlier rows that share the same sorting key. |
| `SummingMergeTree` / `SummingMergeTreeEngine(...)` | `columns` | Numeric columns should be summed during merges. |
| `CollapsingMergeTree` / `CollapsingMergeTreeEngine(...)` | `sign` | You model state and cancel rows explicitly. |
| `VersionedCollapsingMergeTree` / `VersionedCollapsingMergeTreeEngine(...)` | `sign`, `ver` | You need collapsing semantics with explicit version ordering. |
| `AggregatingMergeTree` / `AggregatingMergeTreeEngine()` | None on the table config itself | You are storing aggregate states or simple aggregate values in the table model. |
| `Replicated*MergeTree` engines | `keeperPath`, `replicaName` in TypeScript; `keeper_path`, `replica_name` in Python engine classes | You are running self-managed replicated ClickHouse. Omit both in ClickHouse Cloud. |

`isDeleted` in TypeScript and `is_deleted` in Python require a version column as well.

## Default behavior and constraints

| Behavior | What happens |
| --- | --- |
| Default engine | If you omit `engine`, Moose creates the table with the default `MergeTree` engine. |
| Inferred primary key | `Key` in TypeScript and `Key[...]` in Python mark fields Moose should infer as primary-key columns unless you set `primaryKeyExpression` or `primary_key_expression`. |
| Custom primary key expression | If you set `primaryKeyExpression` or `primary_key_expression`, Moose ignores `Key` annotations for primary-key generation. |
| Ordering config | Use either `orderByFields` or `orderByExpression` in TypeScript, and either `order_by_fields` or `order_by_expression` in Python. Do not set both. |
| Sampling config | `sampleByExpression` or `sample_by_expression` must evaluate to an unsigned integer and must also appear in the `ORDER BY` expression. |
| Versioned table names | If you set `version`, Moose appends that version to the physical table name. For example, `"events"` with version `"1.0"` becomes `events_1_0`. |
| Optional fields with defaults | If a field is optional in your app model but also has a ClickHouse default annotation, Moose keeps it optional at the app layer while generating a non-nullable ClickHouse column with a `DEFAULT` clause. |
| Column comments | TypeScript TSDoc comments and Python `Field(description=...)` or attribute docstrings become ClickHouse column `COMMENT` clauses. |
| Engine-specific clauses | Some engines do not support clauses such as `ORDER BY`, `PARTITION BY`, `SAMPLE BY`, or projections. Match the config fields you set to the capabilities of the chosen engine. |
| Database-qualified names | If you set `database`, Moose qualifies the table as `` `database`.`table_name` `` when it renders SQL references. |

## ReplacingMergeTree example

Use `ReplacingMergeTree` when later rows should replace earlier rows that share the same sorting key.

<LanguageTabs>
  <LanguageTabContent value="typescript">
```ts filename="app/table.ts" copy
import {
  ClickHouseEngines,
  OlapTable,
} from "@514labs/moose-lib";

interface UserSnapshot {
  id: string;
  email: string;
  updatedAt: Date;
  deleted: 0 | 1;
}

export const users = new OlapTable<UserSnapshot>("users", {
  engine: ClickHouseEngines.ReplacingMergeTree,
  orderByFields: ["id"],
  ver: "updatedAt",
  isDeleted: "deleted",
});
```
  </LanguageTabContent>
  <LanguageTabContent value="python">
```py filename="app/table.py" copy
from datetime import datetime

from moose_lib import OlapConfig, OlapTable, ReplacingMergeTreeEngine
from pydantic import BaseModel

class UserSnapshot(BaseModel):
    id: str
    email: str
    updated_at: datetime
    deleted: int

users = OlapTable[UserSnapshot]("users", config=OlapConfig(
    engine=ReplacingMergeTreeEngine(
        ver="updated_at",
        is_deleted="deleted",
    ),
    order_by_fields=["id"],
))
```
  </LanguageTabContent>
</LanguageTabs>
