# ClickHouse Dictionaries

## Overview

`OlapDictionary` is a first-class MooseStack primitive that wraps a [ClickHouse Dictionary](https://clickhouse.com/docs/en/sql-reference/dictionaries) — an in-memory key-value store loaded from a source (a table, a SQL query, or an external system) and refreshed on a configurable schedule.

Dictionaries sit between a source and your queries. Instead of running a `JOIN` at query time, ClickHouse pre-loads the lookup data into memory and serves it via `dictGet`. Reads are O(1) with no network round-trip.

<BulletPointsCard
  title="When to use OlapDictionary"
  bulletStyle="check"
  compact
  bullets={[
    "Enriching streaming data in a MaterializedView (e.g., add product name to click events)",
    "Replacing expensive JOIN operations on small-to-medium lookup tables",
    "Caching external reference data (MySQL, PostgreSQL, MongoDB) close to your queries",
    "Computing dynamic partition keys from a configuration table inside an MV CTE"
  ]}
/>

<Callout type="info" title="ClickHouse 22.4+ required" compact>
`OlapDictionary` uses `CREATE OR REPLACE DICTIONARY` for atomic, zero-downtime updates. This statement requires ClickHouse 22.4 or later.
</Callout>

## Basic Usage

<LanguageTabs>
  <LanguageTabContent value="typescript">
```ts filename="ProductDictionary.ts" copy
import { OlapTable, OlapDictionary, ClickHouseInt, sql } from "@514labs/moose-lib";

interface Product {
  productId: string;
  productName: string;
  category: string;
  priceLevel: number & ClickHouseInt<"Int32">;
  version: number & ClickHouseInt<"UInt64">;
}

export const ProductsTable = new OlapTable<Product>("products", {
  orderByFields: ["productId"],
});

// Dictionary schema — only the columns you need for lookups
interface ProductLookup {
  productId: string;
  productName: string;
  category: string;
  priceLevel: number & ClickHouseInt<"Int32">;
}

export const ProductDict = new OlapDictionary<ProductLookup>("dict_products", {
  sourceTable: ProductsTable,      // auto-tracked dependency
  primaryKey: ["productId"],
  layout: { type: "HASHED" },
  lifetime: { min: 10, max: 15 }, // refresh every 10–15 seconds
  defaults: { category: "Unknown", priceLevel: 0 },
});
```

```python filename="product_dictionary.py" copy
from moose_lib import HashedLayout, DictionaryLifetime
from pydantic import BaseModel
from typing import Annotated
from moose_lib import ClickHouseInt

class Product(BaseModel):
    product_id: str
    product_name: str
    category: str
    price_level: Annotated[int, ClickHouseInt("Int32")]
    version: Annotated[int, ClickHouseInt("UInt64")]

products_table = OlapTable[Product]("products", OlapConfig(
    order_by_fields=["product_id"],
))

# Dictionary schema — only the columns you need for lookups

    product_name: str
    category: str

product_dict = OlapDictionary[ProductLookup](
    name="dict_products",
    config=OlapDictionaryConfig(
        source_table=products_table,       # auto-tracked dependency
        primary_key=["product_id"],
        layout=HashedLayout(),
        lifetime=DictionaryLifetime(min=10, max=15),
        defaults={"category": "Unknown", "price_level": 0},
    ),
)
```

## Source Options

Exactly one source must be specified. Setting zero or more than one is a configuration error caught at startup.

### `sourceTable` / `source_table` — OlapTable or View reference

The simplest option. Moose auto-tracks the dependency: the dictionary is always created after its source and dropped before it.

Generates: `SOURCE(CLICKHOUSE(TABLE 'name' DB 'db'))`

<LanguageTabs>
  <LanguageTabContent value="typescript">
```ts filename="SourceTable.ts" copy
import { OlapDictionary } from "@514labs/moose-lib";
import { ProductsTable } from "./ProductsTable";

export const ProductDict = new OlapDictionary<ProductLookup>("dict_products", {
  sourceTable: ProductsTable,   // OlapTable | View
  primaryKey: ["productId"],
  layout: { type: "HASHED" },
  lifetime: { min: 60, max: 120 },
});
```
  </LanguageTabContent>
  <LanguageTabContent value="python">
```python filename="source_table.py" copy
from moose_lib import OlapDictionary, OlapDictionaryConfig, HashedLayout, DictionaryLifetime
from .products_table import products_table

product_dict = OlapDictionary[ProductLookup](
    name="dict_products",
    config=OlapDictionaryConfig(
        source_table=products_table,  # OlapTable | View
        primary_key=["product_id"],
        layout=HashedLayout(),
        lifetime=DictionaryLifetime(min=60, max=120),
    ),
)
```

### `sourceQuery` / `source_query` — SQL template tag

Use when you need a custom SELECT (e.g. `FINAL`, filters, computed columns). The `sql` template tag is required — raw strings are not accepted. You must also pass `sourceTables` / `source_tables` for dependency tracking.

Generates: `SOURCE(CLICKHOUSE(QUERY 'SELECT ...'))`

<LanguageTabs>
  <LanguageTabContent value="typescript">
```ts filename="SourceQuery.ts" copy
import { OlapDictionary, sql } from "@514labs/moose-lib";
import { ProductsTable } from "./ProductsTable";

export const ProductDict = new OlapDictionary<ProductLookup>("dict_products_final", {
  // Use FINAL to read deduplicated rows from a ReplacingMergeTree
  sourceQuery: sql`SELECT productId, productName, category, priceLevel FROM ${ProductsTable} FINAL`,
  sourceTables: [ProductsTable],  // required for dependency tracking
  primaryKey: ["productId"],
  layout: { type: "HASHED" },
  lifetime: { min: 60, max: 120 },
});
```
  </LanguageTabContent>

### `externalSource` / `external_source` — External systems

Load dictionary data from MySQL, PostgreSQL, MongoDB, HTTP, Redis, or other external systems. Use `mooseRuntimeEnv.get()` / `moose_runtime_env.get()` for all credentials — never hardcode passwords in source code.

<Callout type="warning" title="Credentials must use mooseRuntimeEnv" compact>
Hardcoded credentials appear in plan output, deploy logs, and debug dumps. Always use `mooseRuntimeEnv.get("VAR_NAME")` to reference environment variables. Named Collections are not supported in v1 — use direct connection parameters instead.

## Layout Types

The layout determines how the dictionary is stored in memory and what key types are supported.

### Simple key layouts

Simple key layouts require exactly one `UInt64` primary key column.

| Layout | Parameters | Best for |
|---|---|---|
| `FLAT` | `initialSize?`, `maxSize?` | Small dictionaries (up to ~500k keys); fastest reads |
| `HASHED` | `shards?` | Medium-to-large dictionaries; O(1) lookup |
| `SPARSE_HASHED` | `shards?` | Like HASHED but uses ~3× less memory; slightly slower |
| `HASHED_ARRAY` | (none) | Large dictionaries with numeric keys; cache-friendly |
| `RANGE_HASHED` | `rangeMin`, `rangeMax` | Time-range validity (e.g. price tiers by date range) |
| `CACHE` | `sizeInCells` | Very large dictionaries; LRU cache; misses hit source |
| `SSD_CACHE` | `sizeInCells`, `path` | Dictionaries too large for RAM; spills to SSD |
| `DIRECT` | (none) | No in-memory storage; every lookup queries the source |
| `IP_TRIE` | (none) | IP prefix lookups (CIDR ranges) |

### Complex key layouts

Complex key layouts support multiple primary key columns of any type (use when your key is not a single UInt64).

| Layout | Parameters | Notes |
|---|---|---|
| `COMPLEX_KEY_HASHED` | `shards?` | Most common composite-key layout |
| `COMPLEX_KEY_SPARSE_HASHED` | `shards?` | Memory-efficient variant |
| `COMPLEX_KEY_HASHED_ARRAY` | (none) | Cache-friendly for numeric composite keys |
| `COMPLEX_KEY_RANGE_HASHED` | `rangeMin`, `rangeMax` | Composite key + time range |
| `COMPLEX_KEY_CACHE` | `sizeInCells` | LRU cache for composite keys |
| `COMPLEX_KEY_SSD_CACHE` | `sizeInCells`, `path` | SSD-backed LRU for composite keys |
| `COMPLEX_KEY_DIRECT` | (none) | No in-memory storage; composite key version |

## Lifetime (Refresh Schedule)

| Value | ClickHouse DDL | Behavior |
|---|---|---|
| `0` or `{ min: 0, max: 0 }` | `LIFETIME(0)` | Static — loaded once, never refreshed |
| `number` (seconds) | `LIFETIME(N)` | Refresh every N seconds |
| `{ min: N, max: M }` | `LIFETIME(MIN N MAX M)` | Refresh on a random interval between N and M seconds (avoids thundering herd) |

<LanguageTabs>
  <LanguageTabContent value="typescript">
```ts
// Static — never refreshed (use for immutable reference data)
lifetime: 0

// Every 300 seconds
lifetime: 300

// Random interval between 60 and 120 seconds
lifetime: { min: 60, max: 120 }
```

## Lifecycle Management

The `lifeCycle` / `life_cycle` option controls how Moose manages DDL for this dictionary.

| Value | Behavior |
|---|---|
| `LifeCycle.FULLY_MANAGED` (default) | Moose creates, updates, and drops the dictionary |
| `LifeCycle.DELETION_PROTECTED` | Moose creates and updates but never drops — safe for production dictionaries |
| `LifeCycle.EXTERNALLY_MANAGED` | Moose never touches the dictionary; use to reference dictionaries managed outside Moose |

<LanguageTabs>
  <LanguageTabContent value="typescript">
```ts filename="Lifecycle.ts" copy

  sourceTable: ProductsTable,
  primaryKey: ["productId"],

  lifeCycle: LifeCycle.DELETION_PROTECTED,
```

## Helper Methods

Use these typed methods inside `sql` template tags to call `dictGet` / `dictGetOrDefault` / `dictHas` in your queries and materialized views. When used via the `sql` tag, Moose tracks the dictionary as a dependency of the consuming view.

<Callout type="warning" title="Dependency tracking requires the sql tag" compact>
Moose only tracks dictionary-to-view dependencies when the helper is interpolated via the `sql` template tag (e.g. `${dict.get("col", sql\`key\`)}`). Raw `dictGet(...)` strings in SQL are not tracked and will not guarantee correct DDL ordering.
</Callout>

### `get(attribute, key)` — `dictGet`

Returns the attribute value for the given key. If the key is not found, returns the column's default value (zero, empty string, etc.) or the `defaults` value you configured.

<LanguageTabs>
  <LanguageTabContent value="typescript">
```ts filename="GetHelper.ts" copy
import { MaterializedView, sql } from "@514labs/moose-lib";
import { ProductDict } from "./ProductDictionary";
import { RawClicksTable, ClicksTable } from "./ClicksTables";

interface EnrichedClick {
  clickId: string;
  productId: string;
  productName: string;
  category: string;
  clickedAt: Date;
}

export const EnrichClicksMV = new MaterializedView<EnrichedClick>({
  selectStatement: sql`
    SELECT
      clickId,
      productId,
      ${ProductDict.get("productName", sql`productId`)} AS productName,
      ${ProductDict.get("category", sql`productId`)}    AS category,
      clickedAt
    FROM ${RawClicksTable}
  `,
  selectTables: [RawClicksTable],
  targetTable: {
    name: "enriched_clicks",
    orderByFields: ["clickId"],
  },
  materializedViewName: "mv_enrich_clicks",
});
// Generates: dictGet('local.dict_products', 'productName', productId)
```
  </LanguageTabContent>
  <LanguageTabContent value="python">
```python filename="get_helper.py" copy
from moose_lib import MaterializedView, MaterializedViewOptions, sql
from .product_dictionary import product_dict
from .clicks_tables import raw_clicks_table, clicks_table

class EnrichedClick(BaseModel):
    click_id: str
    product_id: str
    product_name: str
    category: str
    clicked_at: datetime

enrich_clicks_mv = MaterializedView[EnrichedClick](MaterializedViewOptions(
    select_statement=f"""
        SELECT
            click_id,
            product_id,
            {product_dict.get("product_name", "product_id")} AS product_name,
            {product_dict.get("category", "product_id")}     AS category,
            clicked_at
        FROM {raw_clicks_table}
    """,
    select_tables=[raw_clicks_table],
    target_table=clicks_table,
    materialized_view_name="mv_enrich_clicks",
))
```
  </LanguageTabContent>
</LanguageTabs>

### `getOrDefault(attribute, key, default)` — `dictGetOrDefault`

Like `get()` but lets you specify a fallback at the call site rather than relying on the column default. For composite keys, the key argument is automatically wrapped in `tuple()`.

<LanguageTabs>
  <LanguageTabContent value="typescript">
```ts
// Single key
${ProductDict.getOrDefault("category", sql`productId`, sql`'Uncategorized'`)}

// Composite key — tuple() wrapping is automatic
${PartitionDict.getOrDefault("strategy", sql`tableName, shardId`, sql`'WEEK'`)}
// Generates: dictGetOrDefault('local.dict_partitions', 'strategy', tuple(tableName, shardId), 'WEEK')
```
  </LanguageTabContent>
  <LanguageTabContent value="python">
```python
# Single key
product_dict.get_or_default("category", "product_id", "'Uncategorized'")

# Composite key — tuple() wrapping is automatic
partition_dict.get_or_default("strategy", ("table_name", "shard_id"), "'WEEK'")
```
  </LanguageTabContent>
</LanguageTabs>
