# Tutorial: Production-Ready Analytics Agent

The harness is the full development environment for building production analytics agents with MooseStack. It includes:

- **MooseStack Framework** — TypeScript interfaces for ClickHouse and real-time analytical infrastructure, designed to be readable and writable by coding agents
- **MooseStack CLI** — agent-friendly CLI for initializing projects, running queries, and inspecting infrastructure
- **Dev Server** — runs the full stack locally, hot-swaps code changes, gives your agent a live environment to work against
- **MCP Server + LSP** — agent-friendly interfaces for troubleshooting: logs, errors, schema introspection, query results
- **Agent Skills** — ClickHouse and data engineering best practices packaged as skills your coding agent can invoke
- **Template** — the `typescript-agent` skeleton reference implementation with the production plumbing already wired: auth, tenant isolation, multi-agent orchestration, observability, semantic layer, guardrails

Section 1 sets up the harness. Once it's running, every subsequent section can be executed by your coding agent.

<Callout type="info" title="Three ways to use this guide">
1. **Manually** — read each step and run the commands yourself
2. **With your coding agent** — point Claude Code, Cursor, or Kiro at this guide and let it execute each section; the harness gives it the context and tools it needs
3. **Hybrid** — run setup steps yourself, hand off domain-specific work (data modeling, prompt tuning, adding specialists) to your coding agent
</Callout>

## Configure the Template

<GuideStepper id="agent-configure" persist>

<GuideStepper.Step id="configure" number={1} title="Configure AI Provider, Observability, and Guardrails" summary="Connect your AI provider, enable Langfuse tracing, and verify chat is working">
<GuideStepper.WhatYouNeed>
  - Running harness from Section 1
  - API credentials for your chosen AI provider
</GuideStepper.WhatYouNeed>
<GuideStepper.WhatYouGet>
  - Chat panel active and streaming responses
  - Langfuse traces landing (optional but recommended now)
</GuideStepper.WhatYouGet>

<GuideStepper.Checkpoint id="ai-provider" title="Connect your AI provider">

Edit `packages/web-app/.env.local`:

| Provider | Variables |
|---|---|
| Anthropic | `AI_PROVIDER=anthropic`, `ANTHROPIC_API_KEY=sk-ant-...`, optional `ANTHROPIC_MODEL_ID` |
| OpenAI | `AI_PROVIDER=openai`, `OPENAI_API_KEY=sk-...`, optional `OPENAI_MODEL_ID` |
| AWS Bedrock | `AI_PROVIDER=bedrock`, `AWS_REGION=us-east-1`, `BEDROCK_MODEL_ID=...`, optional `AWS_PROFILE` or `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` |

Restart services after editing: `Ctrl-C` then `pnpm dev:start`. For web-app-only changes, `pnpm dev:web` can be restarted independently.

<Callout type="info" title="Bedrock tool schema note">
When writing custom MCP tools for Bedrock, prefer `z.string()` with explicit allowed-value descriptions over `z.enum()`. Bedrock tool-schema validation is stricter than Anthropic/OpenAI, and the template's built-in tools are already on this path.
</Callout>

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="guardrails" title="(Optional) Enable AWS Bedrock Guardrails">

Guardrails are a Bedrock-only feature in this template. Non-Bedrock providers use a silent pass-through (`NoopGuardrailAdapter`). If `AI_PROVIDER=bedrock`:

| Variable | Purpose |
|---|---|
| `BEDROCK_GUARDRAIL_ID` | Enables real Guardrails content policy checks |
| `BEDROCK_GUARDRAIL_VERSION` | Defaults to `DRAFT` if omitted |

Without these set, local development uses a pattern-matching mock (`DevelopmentMockGuardrailAdapter` in `packages/web-app/src/dev/mock-guardrails.ts`). In production without these vars, guardrails are silently disabled. Come back to this in Section 5 if you're using Bedrock.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="langfuse" title="Enable Langfuse observability">

Sign up at [cloud.langfuse.com](https://cloud.langfuse.com), create a project, and copy the Public and Secret keys from project settings.

Add to `packages/web-app/.env.local`:

| Variable | Purpose |
|---|---|
| `LANGFUSE_PUBLIC_KEY` | Enables tracing (starts with `pk-lf-...`) |
| `LANGFUSE_SECRET_KEY` | Enables tracing (starts with `sk-lf-...`) |
| `LANGFUSE_BASE_URL` | Optional — defaults to `https://cloud.langfuse.com`; set for self-hosted |

Without these, the template uses an in-memory fallback collector — the app works but nothing is recorded externally. You can add these now or return to them in Section 5.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="verify-chat" title="Verify chat is working">

Open `http://localhost:3000`, sign in, and ask a data question.

You'll see the multi-agent pattern in the streamed response: `[AGENT:supervisor]` → `[AGENT:<specialist>]` → `[AGENT:narrator]`.

If you've configured Langfuse, check your dashboard to confirm a trace landed with spans for each agent step.

</GuideStepper.Checkpoint>

</GuideStepper.Step>

</GuideStepper>

<ToggleBlock openText="Using the Amazon Customer Reviews dataset?" closeText="Hide Amazon dataset example">
The [Amazon Customer Reviews dataset](https://clickhouse.com/docs/getting-started/example-datasets/amazon-reviews) has 150M+ product reviews in Parquet on S3. The schema is documented on that page, so you can point your agent directly at it.

To grab sample data locally:

```shell
moose query "
  SELECT * FROM s3(
    'https://datasets-documentation.s3.eu-west-3.amazonaws.com/amazon_reviews/amazon_reviews_2015.snappy.parquet'
  ) LIMIT 10;
"
```
</ToggleBlock>

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="create-data-model" title="Create a data model">

Key file: `packages/moosestack-service/app/ingest/models.ts`

Ask your coding agent to replace the `TenantKnowledge` model. Invoke the `/moosestack-clickhouse-best-practices` skill for efficient typing and `orderBy` choices.

<GuideStepper.Prompt>
Replace the TenantKnowledge interface and IngestPipeline in
packages/moosestack-service/app/ingest/models.ts with a model for [your domain].
Keep the tenant_id field and SelectRowPolicy for multi-tenant isolation.
Follow ClickHouse best practices for typing and orderBy — invoke the
/moosestack-clickhouse-best-practices skill.
Export the new table from app/index.ts.
</GuideStepper.Prompt>

Key considerations:
- **Typing matters**: use tight types, `LowCardinality` for low-cardinality strings, appropriate numeric precision
- **Order By is critical**: the `orderBy` determines how data is physically stored in ClickHouse — think about how the data will be queried and filtered
- **Keep `tenant_id`**: this field is required for the row-level security policy

<Callout type="info" title="MCP tools are automatically scoped">
Tables included in the `SelectRowPolicy` are automatically exposed to MCP tools (`get_data_catalog`, `query_clickhouse`). No manual edits to `exposed-surface.ts` are needed — just make sure your table is in the `tables` array of the `tenantIsolation` policy.
</Callout>

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="load-flat-file" title="Option A: Load a flat file">

If you have data in a flat file (Parquet, CSV, etc.) accessible via S3 or a URL, write a SQL file to insert it:

```sql
-- load-data.sql
INSERT INTO local.YourTable
  SELECT * FROM s3(
    's3://your-bucket/path/to/file.parquet',
    '<Access-Key-ID>',
    '<Secret-Access-Key>',
    'Parquet'
  );
```

Then execute it with:

```shell
moose query -f load-data.sql
```

In production, use `514 query` to run the same SQL against your hosted ClickHouse.

<GuideStepper.Checkpoint id="agent-flow" title="The supervisor → specialist → narrator flow">

The chat output shows the handoff markers you saw in Section 2: `[AGENT:supervisor]` → `[AGENT:<specialist>]` → `[AGENT:narrator]`.

- The **supervisor** receives the user's message and routes it to the appropriate specialist
- The **specialist** has access to the MCP tools (`query_clickhouse`, `get_data_catalog`) and generates the data response
- The **narrator** takes the specialist's output and formats it into a clear, natural-language answer

| File | Role |
|---|---|
| `packages/agent-runtime/src/prompts/multi-agent.ts` | Supervisor selection logic and specialist system prompts |
| `packages/agent-runtime/src/index.ts` | Orchestration and stream creation |
| `packages/web-app/src/lib/chat-agent.ts` | Next.js-hosted adapter — injects auth, Langfuse trace collector, and guardrail adapter |

- Are SQL queries appropriately selective, or are there unexpectedly broad scans?

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="identify-patterns" title="Identify query patterns from chat usage">

Right now, the chat generates SQL on the fly. That works for exploration, but the moment the same metric lives in chat, an API, a dashboard, and an MCP tool, you have multiple SQL definitions that can drift.

Before building the query layer, understand what queries your agent is actually running. Review the `query_clickhouse` tool call results in your chat UI — each one shows the SQL that was executed.

Look for:
- Repeated aggregation patterns (e.g., `GROUP BY date`, `COUNT(*)`)
- Metrics that should have constraints (e.g., revenue should only count completed transactions)
- Common filter and grouping combinations

These patterns become the dimensions, metrics, and filters in your query model.

<Callout type="info" title="Materialized Views for heavy metrics">
For compute-heavy metrics, consider backing your query model with a [Materialized View](https://docs.fiveonefour.com/moosestack/materialized-views?lang=typescript) that pre-aggregates data. The query model references the MV's target table instead of the raw data.
</Callout>

</GuideStepper.Checkpoint>

| Variable | Notes |

| Variable | Notes |
|---|---|

| `OIDC_ISSUER` | Your OIDC provider's issuer URL |
| `OIDC_CLIENT_ID` | Client ID |
| `OIDC_CLIENT_SECRET` | Client secret |
| `OIDC_TENANT_CLAIM` | JWT claim containing the tenant identifier |
