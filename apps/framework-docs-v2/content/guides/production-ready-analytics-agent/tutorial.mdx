## Configure the Template

The template ships configured for local development with mock auth and a passthrough observability collector. This section connects the real services: an AI provider for the analytics agents, Langfuse for traces, and optionally Bedrock Guardrails.

<Callout type="info" title="AI provider vs. coding agent">
The AI provider you configure here is for the **analytics agents running inside the application** — the supervisor, specialist, and narrator that respond to user queries. This is separate from the coding agent (Claude Code, Cursor, etc.) you're using to build the app.
</Callout>

<GuideStepper id="agent-configure" persist>

<GuideStepper.Step id="configure" number={1} title="Configure AI provider, observability, and guardrails" summary="Connect your AI provider, enable Langfuse tracing, and confirm the template is wired up correctly">
<GuideStepper.WhatYouNeed>
  - Coding Agent Harness running from Section 1
  - API credentials for your chosen AI provider
</GuideStepper.WhatYouNeed>
<GuideStepper.WhatYouGet>
  - Analytics agents connected to your AI provider
  - Langfuse traces landing (optional but recommended now)
</GuideStepper.WhatYouGet>

<GuideStepper.Checkpoint id="ai-provider" title="Connect your AI provider">

Edit `packages/web-app/.env.local`:

| Provider | Variables |
|---|---|
| Anthropic | `AI_PROVIDER=anthropic`, `ANTHROPIC_API_KEY=sk-ant-...`, optional `ANTHROPIC_MODEL_ID` |
| OpenAI | `AI_PROVIDER=openai`, `OPENAI_API_KEY=sk-...`, optional `OPENAI_MODEL_ID` |
| AWS Bedrock | `AI_PROVIDER=bedrock`, `AWS_REGION=us-east-1`, `BEDROCK_MODEL_ID=...`, optional `AWS_PROFILE` or `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` |

Restart services after editing: `Ctrl-C` then `pnpm dev:start`. For web-app-only changes, `pnpm dev:web` can be restarted independently.

<Callout type="info" title="Bedrock tool schema note">
When writing custom MCP tools for Bedrock, prefer `z.string()` with explicit allowed-value descriptions over `z.enum()`. Bedrock tool-schema validation is stricter than Anthropic/OpenAI, and the template's built-in tools are already on this path.
</Callout>

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="guardrails" title="(Optional) Enable AWS Bedrock Guardrails">

Guardrails are a Bedrock-only feature in this template. Non-Bedrock providers use a silent pass-through (`NoopGuardrailAdapter`). If `AI_PROVIDER=bedrock`:

| Variable | Purpose |
|---|---|
| `BEDROCK_GUARDRAIL_ID` | Enables real Guardrails content policy checks |
| `BEDROCK_GUARDRAIL_VERSION` | Defaults to `DRAFT` if omitted |

Without these set, local development uses a pattern-matching mock (`DevelopmentMockGuardrailAdapter` in `packages/web-app/src/dev/mock-guardrails.ts`). In production without these vars, guardrails are silently disabled. Come back to this in Section 5 if you're using Bedrock.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="langfuse" title="Enable Langfuse observability">

Sign up at [cloud.langfuse.com](https://cloud.langfuse.com), create a project, and copy the Public and Secret keys from project settings.

Add to `packages/web-app/.env.local`:

| Variable | Purpose |
|---|---|
| `LANGFUSE_PUBLIC_KEY` | Enables tracing (starts with `pk-lf-...`) |
| `LANGFUSE_SECRET_KEY` | Enables tracing (starts with `sk-lf-...`) |
| `LANGFUSE_BASE_URL` | Optional — defaults to `https://cloud.langfuse.com`; set for self-hosted |

Without these, the template uses an in-memory fallback collector — the app works but nothing is recorded externally. You can add these now or return to them in Section 5.

</GuideStepper.Checkpoint>

</GuideStepper.Step>

</GuideStepper>

**Section 2 complete.** To verify: open `http://localhost:3000`, sign in as `acme`, and send a chat message. You should see the multi-agent pattern in the streamed response: `[AGENT:supervisor]` → `[AGENT:<specialist>]` → `[AGENT:narrator]`. The response may be vague or generic — the demo data is fake placeholder data, not your domain. That's expected. What you're confirming here is that the template is wired correctly: auth works, the AI provider is connected, and the agent pipeline is running. You'll verify the agent can actually answer useful questions in Section 3, once real data is in.

## Get Your Data In

The template's demo model (`TenantKnowledge`) is a stand-in to confirm setup. This section replaces it with your domain data.

The order matters: **load a sample first, then model it, then load everything.** Your coding agent needs to see real data — actual column types, cardinalities, and example values — before it can define an accurate ClickHouse schema. Don't define the model from docs alone if you can get a sample.

There are three common paths depending on your data source:

- **Data dump** — a CSV, Parquet, or SQL export. Fastest path to get started.
- **API or scheduled pull** — create a MooseStack Workflow that fetches from your source on a schedule.
- **Live database replication (CDC)** — connect a running Postgres or MySQL database. See the [Performant Dashboards guide](/guides/performant-dashboards) for full CDC setup with ClickPipes or Debezium.

All three follow the same sequence in the steps below: sample → model → full load.

<GuideStepper.Checkpoint id="create-data-model" title="Create the data model">

Key file: `packages/moosestack-service/app/ingest/models.ts`

<GuideStepper.Prompt>
Replace the TenantKnowledge interface and IngestPipeline in
packages/moosestack-service/app/ingest/models.ts with a model for [your domain].
Use the sample data already in ClickHouse to inform column types and cardinalities.
Keep the tenant_id field and SelectRowPolicy for multi-tenant isolation.

Key considerations:
- **Typing matters**: use tight types, `LowCardinality` for low-cardinality strings, appropriate numeric precision

</Callout>

<GuideStepper.Checkpoint id="agent-flow" title="The supervisor → specialist → narrator flow">

The handoff markers in the streamed response (`[AGENT:supervisor]` → `[AGENT:<specialist>]` → `[AGENT:narrator]`) show the pipeline in action:

- The **supervisor** receives the user's message and routes it to the appropriate specialist
- The **specialist** has access to the MCP tools (`query_clickhouse`, `get_data_catalog`) and generates the data response
- The **narrator** takes the specialist's output and formats it into a clear, natural-language answer

| File | Role |
|---|---|
| `packages/agent-runtime/src/prompts/multi-agent.ts` | Supervisor selection logic and specialist system prompts |
| `packages/agent-runtime/src/index.ts` | Orchestration and stream creation |
| `packages/web-app/src/lib/chat-agent.ts` | Next.js-hosted adapter — injects auth, Langfuse trace collector, and guardrail adapter |

</GuideStepper.Checkpoint>

## Harden for Production

<GuideStepper id="agent-harden" persist>

<GuideStepper.Checkpoint id="identify-patterns" title="Identify query patterns from chat usage">

Right now, the chat generates SQL on the fly. That works for exploration, but the moment the same metric lives in chat, an API, a dashboard, and an MCP tool, you have multiple SQL definitions that can drift.

Review the `query_clickhouse` tool call results in your chat UI — each one shows the SQL that was executed. Look for:
- Repeated aggregation patterns (e.g., `GROUP BY date`, `COUNT(*)`)
- Metrics that should have constraints (e.g., revenue should only count completed transactions)
- Common filter and grouping combinations

These patterns become the dimensions, metrics, and filters in your query model.

<Callout type="info" title="Materialized Views for heavy metrics">
For compute-heavy metrics, consider backing your query model with a [Materialized View](https://docs.fiveonefour.com/moosestack/materialized-views?lang=typescript) that pre-aggregates data. The query model references the MV's target table instead of the raw data.
</Callout>

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="review-query-model" title="Review the generated query model">

- **Dimensions** cover the groupings you need (time buckets, categories, etc.)

- **Filters** expose the right columns and operators for your use cases
- **Column references** use `YourTable.columns.*` (not raw strings) for type safety
- **Descriptions** are clear — they propagate to tool definitions and help the LLM

</GuideStepper.Checkpoint>

**Validated:** Every surface — chat, APIs, dashboards, MCP — now shares one set of metric definitions. If a metric changes, it changes once.

The template is pre-configured for deployment to 514 hosting (MooseStack service) and Vercel (Next.js web app). Preview environments are provisioned automatically per PR — each branch gets an isolated ClickHouse database so schema changes can be validated before merging.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="514-env-vars" title="Set production environment variables">

In 514 hosting project settings, add:

| Variable | Notes |
|---|---|
| `AI_PROVIDER` + provider credentials | Same as your local setup |
| `LANGFUSE_PUBLIC_KEY` + `LANGFUSE_SECRET_KEY` | From your Langfuse project |
| `BEDROCK_GUARDRAIL_ID` + `BEDROCK_GUARDRAIL_VERSION` | If using Bedrock Guardrails |
| `MOOSE_JWT__SECRET` | Your production OIDC provider's PEM public key (replaces the local RSA key) |

**For production OIDC** (replacing the built-in local mock auth):

| Variable | Notes |
|---|---|
| `MOOSE_AUTH_MODE=oidc` | Switches from local mock to real OIDC |
| `OIDC_ISSUER` | Your OIDC provider's issuer URL |
| `OIDC_CLIENT_ID` | Client ID |
| `OIDC_CLIENT_SECRET` | Client secret |
| `OIDC_TENANT_CLAIM` | JWT claim containing the tenant identifier |

Also update the `[jwt]` issuer/audience in `packages/moosestack-service/moose.config.toml`.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint id="deploy-moose" title="Deploy">

Push to main to deploy. Open a feature branch and create a PR to get a preview environment — 514 provisions an isolated ClickHouse database per branch so schema changes can be validated before merging.

</GuideStepper.Checkpoint>

**Validated:** MooseStack service is live at your 514 hosting URL. A PR preview environment is provisioned and accessible.
