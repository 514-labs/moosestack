# Overview

## Why analytics agents

An analytics agent isn't a better search box. It's a qualitatively different interface: users ask questions in natural language, and the system responds by querying the actual systems of record — live, structured data — not a summarized document corpus or a static dashboard. The model inspects schemas, runs SQL, computes aggregates, and explains real results.

That changes what's possible. Analytics products can let users explore data freely instead of navigating pre-built dashboards. Internal tooling teams can give non-technical stakeholders direct access to metrics without building a new interface for every question. Customer-facing products can surface insights that would otherwise require analyst involvement. The same agent that answers a free-form question can also power deterministic API endpoints and MCP tools — all from the same data surface.

## The analytics agent harness

An analytics agent prototype is straightforward to build. Getting it to production is where teams stall — because the agent alone isn't enough. You need an analytics agent harness around it.

The analytics agent harness is everything that makes your analytics agent production-ready: the high-performance analytical infrastructure (ClickHouse), the APIs and MCP tools that expose data to the agent, and the operational layer that enforces security, captures traces, keeps metrics consistent, and applies guardrails. ClickHouse isn't separate from the harness — it's the foundation of it. What we're building in this guide is the analytics agent harness.

Most analytics agent prototypes work in demos and break under real conditions. The problems aren't hard to name — they're just easy to defer until they become incidents.

## Architecture

```
                    ┌──────────────────────────────────────┐
                    │      Analytics Agent Harness         │
Source Data ───────►│  ClickHouse · APIs · MCPs            │───► Analytics Agent ───► Next.js GUI
                    │  Security · Observability            │
                    │  Semantic Layer · Guardrails         │
                    └──────────────────────────────────────┘
```

Source data flows into the Analytics Agent Harness, which stores and serves it through ClickHouse, exposes it to the analytics agent through APIs and MCP tools, and enforces the operational layer: tenant security, observability, semantic consistency, and guardrails. The analytics agent queries that surface and streams results to the Next.js UI.

How you build and configure this — the Coding Agent Harness — is covered on the [Dev Approach](/guides/production-ready-analytics-agent/dev-approach) page.

## When this approach is worth building

This is the right foundation when: the product has meaningful data gravity, users ask questions that can't be pre-built as dashboards, and the same data surface needs to power chat, APIs, and dashboards consistently. The overhead is real — you're setting up a full OLAP stack, multi-agent runtime, auth, and observability. That overhead pays off when the data complexity warrants it.

It's overkill for a thin UI over an existing API. If you need LLM-assisted responses but don't need ClickHouse, tenant isolation, or a semantic layer, start with [Chat in Your App](/guides/chat-in-your-app) — the same stack without the multi-tenant production requirements.
