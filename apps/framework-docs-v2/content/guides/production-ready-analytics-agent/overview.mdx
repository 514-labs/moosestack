# Overview

## Why build your own Analytics Agent

An analytics agent lets users ask questions in natural language and get answers from your actual data — live, structured data queried directly, not a summarized document corpus or a pre-built dashboard. The model inspects schemas, runs SQL, computes aggregates, and explains real results.

That changes what's possible. Users explore data freely instead of waiting on analysts. Non-technical stakeholders get direct access to metrics. The same agent that answers a free-form question can also power deterministic API endpoints and MCP tools — all from the same data surface.

BI providers offer off-the-shelf analytics agents. Here's why you'd build your own instead:

- **You own the code and the full logic.** No black box. Every decision about how queries are constructed, how results are explained, and how the agent behaves is yours to inspect, modify, and improve.
- **Custom security and auth.** Your tenancy model, your JWT flow, your row-level policies — enforced exactly how your product requires, not how a vendor decided to implement it.
- **Custom semantics.** Your definition of "revenue", "active users", or "churn" — not a vendor's approximation. The agent speaks your domain, with the exact metric definitions your business relies on.
- **Performance you can optimize.** You control the query layer, the ClickHouse schema, the caching strategy. You can tune for your data shape, your query patterns, your scale — not a generic workload.
- **It's your agent.** You can extend it, specialize it, integrate it with anything, and ship it on your timeline.

## What makes an Analytics Agent "production-ready"?

An analytics agent prototype is straightforward to build. Getting it to production is where teams stall. The problems aren't hard to name — they're just easy to defer until they become incidents.

## Building an Analytics Agent Harness

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                                 Your Analytics Agent App                                 │
│                                                                                          │
│  ┌─────────────┐   ┌─────────────────────────────────┐   ┌─────────────┐   ┌──────────┐  │
│  │ Source Data │──►│     Analytics Agent Harness     │──►│  Analytics  │──►│ Next.js  │  │
│  └─────────────┘   │  ClickHouse · APIs · MCPs       │   │    Agent    │   │   GUI    │  │
│                    │  Security · Observability       │   └─────────────┘   └──────────┘  │
│                    │  Semantic Layer · Guardrails    │                                   │
│                    └─────────────────────────────────┘                                   │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

The Analytics Agent Harness is the layer that makes the analytics agent production-ready. You don't just need to build the agent - you need to build the harness too. Source data flows in, gets stored in ClickHouse, and is exposed to the analytics agent through APIs and MCP tools. The harness layer enforces tenant security, captures traces, keeps metrics consistent, and applies guardrails. The analytics agent queries that surface and streams results to the Next.js UI.

## When this approach is worth building

This is the right foundation when: the product has meaningful data gravity, users ask questions that can't be pre-built as dashboards, and the same data surface needs to power chat, APIs, and dashboards consistently. The overhead is real — you're setting up a full OLAP stack, multi-agent runtime, auth, and observability. That overhead pays off when the data complexity or the security posture warrants it.
