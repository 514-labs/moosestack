# Overview

## Why analytics agents

An analytics agent isn't a better search box. It's a qualitatively different interface: users ask questions in natural language, and the system responds by querying the actual systems of record — live, structured data — not a summarized document corpus or a static dashboard. The model inspects schemas, runs SQL, computes aggregates, and explains real results.

That changes what's possible. Analytics products can let users explore data freely instead of navigating pre-built dashboards. Internal tooling teams can give non-technical stakeholders direct access to metrics without building a new interface for every question. Customer-facing products can surface insights that would otherwise require analyst involvement. The same agent that answers a free-form question can also power deterministic API endpoints and MCP tools — all from the same data surface.

## Getting to production

An analytics agent prototype is straightforward to build. Getting it to production is where teams stall. The problems aren't hard to name — they're just easy to defer until they become incidents.

<BulletPointsCard
  title="Common pitfalls"
  bulletStyle="x"
  bullets={[

      description:
        "An agent hitting a transactional database works in demos and fails under real data volume and concurrency. Analytical queries at scale need a purpose-built OLAP engine.",

      description:
        "Tenant isolation enforced at the application layer can be bypassed — by a bug, a prompt injection, or a misconfiguration. Application-layer checks aren't sufficient.",
    },
    {

      description:
        "Without traces you can't see what SQL the agent generated, what it cost, or where latency went. You can't tune what you can't measure, and you can't debug an incident without a record of what happened.",

    {
      title: "Semantic consistency",
      description:
        "The same metric defined in five places will drift. Chat, APIs, dashboards, and MCP tools each develop their own SQL definition of 'revenue' or 'active users', and they start returning different numbers.",
    },
    {
      title: "Guardrails",
      description:
        "Content policy enforcement bolted on after a production incident is harder to audit and easier to miss.",
    },
  ]}

## The Analytics Agent Harness

```

│  │ Source Data │──►│     Analytics Agent Harness     │──►│  Analytics  │──►│ Next.js  │  │
│  └─────────────┘   │  ClickHouse · APIs · MCPs       │   │    Agent    │   │   GUI    │  │
│                    │  Security · Observability       │   └─────────────┘   └──────────┘  │
│                    │  Semantic Layer · Guardrails    │                                   │
│                    └─────────────────────────────────┘                                   │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

The Analytics Agent Harness is the layer that makes the analytics agent production-ready. Source data flows in, gets stored in ClickHouse, and is exposed to the analytics agent through APIs and MCP tools. The operational layer enforces tenant security, captures traces, keeps metrics consistent, and applies guardrails. The analytics agent queries that surface and streams results to the Next.js UI.

## When this approach is worth building

This is the right foundation when: the product has meaningful data gravity, users ask questions that can't be pre-built as dashboards, and the same data surface needs to power chat, APIs, and dashboards consistently. The overhead is real — you're setting up a full OLAP stack, multi-agent runtime, auth, and observability. That overhead pays off when the data complexity or the security posture warrants it.
