# Tutorial v2: Production-Ready Analytics Agent

This tutorial will guide you (or your coding agent!) step-by-step through building out a production-ready analytics agent — an AI agent that can query data, extract insights, and present findings safely, reliably, and fast.

The foundation of this tutorial is a [highly composable template](https://github.com/514-labs/moosestack/tree/main/templates/typescript-agent), with best practices for analytical agents and infrastructure included, so you can focus on your domain instead of plumbing.

## 1. Get Running

This step uses the [`typescript-agent` template](https://github.com/514-labs/moosestack/tree/main/templates/typescript-agent) — a production-shaped starter with agent runtime, ClickHouse-backed data, JWT-friendly auth, and MCP tools wired together.

### Install the CLIs

**Option A — Editor extension (VS Code, Cursor, Kiro)**  
Install the [514 Harness extension](https://marketplace.visualstudio.com/items?itemName=514-labs.fiveonefour). After install, use **Install Harness** on the splash screen to provision the `514` and `moose` CLIs.

**Option B — Bash (any terminal)**

```bash
bash -i <(curl -fsSL https://fiveonefour.com/install.sh) 514,moose
```

Verify with `moose --version` and `514 --version`. For prerequisites and troubleshooting, see the [Quickstart](/moosestack/getting-started/quickstart).

### Create your project

Interactive wizard:

```bash
moose harness init
```

Select the **typescript-agent** template, project name, coding agent(s), and whether to use local Docker ClickHouse or a remote cluster.

Non-interactive (agents or CI):

```bash
moose harness init \
  --name <project-name> \
  --agent claude-code \
  --agent cursor \
  --lsp \
  --template typescript-agent
```

Repeat `--agent` for each editor or tool you use; run `moose harness init --help` for the current flag list. Add `--clickhouse-url <url>` to attach an existing ClickHouse instance.

The harness flow installs skills, MCP config for your coding agents, and the MooseStack LSP — more than a plain `moose init`.

### Validate the harness

After initialization, confirm:

- **Skills** — Your coding agent should see skills such as `514--cli`, `514--debug`, and `clickhouse--best-practices` (paths vary by product; with Claude Code, `/skills` lists them).
- **MCP** — `moose-dev` (or equivalent) should appear in your agent’s MCP server list; tools light up once the dev server is running.
- **LSP** — `moosestack-lsp` should be on your PATH for model editing support.

Restart the coding agent session if new config does not appear immediately.

### Project layout

You get a pnpm monorepo similar to:

- `packages/moosestack-service/` — models, ingest, workflows, MCP server, HTTP APIs
- `packages/web-app/` — Next.js UI and chat
- `packages/agent-runtime/` — prompts and stream creation
- `packages/agent-contracts/` — shared types

### Install dependencies and prepare environment

```bash
cd <project-name>
pnpm install
pnpm env:prepare
```

`pnpm env:prepare` creates `.env.local` files from examples, generates `AUTH_SECRET`, and creates a local RSA keypair for the mock tenant JWT flow.

### Configure your AI provider (analytics agents)

Edit `packages/web-app/.env.local`. The **AI provider here powers the in-app analytics agent**, not your coding agent.

| Provider   | Variables |
| ---------- | --------- |
| Anthropic  | `AI_PROVIDER=anthropic`, `ANTHROPIC_API_KEY=...`, optional `ANTHROPIC_MODEL_ID` |
| OpenAI     | `AI_PROVIDER=openai`, `OPENAI_API_KEY=...`, optional `OPENAI_MODEL_ID` |
| AWS Bedrock | `AI_PROVIDER=bedrock`, `AWS_REGION`, `BEDROCK_MODEL_ID`, plus `AWS_PROFILE` or access keys |

<Callout type="info" title="Bedrock tool schemas">
For custom MCP tools with Bedrock, prefer `z.string()` with explicit allowed values in descriptions over `z.enum()` — Bedrock’s tool-schema validation is stricter than Anthropic/OpenAI.
</Callout>

### Start the dev stack

```bash
pnpm dev:start
```

Requires Docker Desktop or Docker Engine (or Finch with `MOOSE_DEV__CONTAINER_CLI_PATH` set). This starts ClickHouse, the Moose service (including MCP), and the Next.js app. Keep this process running.

- Moose / MCP: `http://localhost:4000` (MCP tools under `/tools`)
- Web app: `http://localhost:3000`

### Seed demo data and verify chat

In a second terminal:

```bash
pnpm seed
```

Open `http://localhost:3000`, choose a demo tenant, open the dashboard and chat, and send a message. **You’re ready to continue when** you get a streamed response and see tool activity in the UI (and optionally `[AGENT:...]` markers if you’re on a multi-agent configuration).

Sign out and sign in as the other demo tenant to confirm tenant-scoped data changes — that validates the template’s isolation story before you replace models with your own.

### Running example: ADS-B / aircraft tracker

For a concrete end-to-end that loads live military ADS-B data, polls an API on a schedule, and builds query models on top, use the **[aircraft-tracker example](https://github.com/514-labs/moosestack/tree/add-example-apps/examples/aircraft-tracker)** in the MooseStack repo (paths such as `app/ingest/models.ts`, `app/workflows/`, `app/query-models/` or `app/semantic/` may differ slightly by revision — follow that repo’s layout). A quick shape check against the public API:

```bash
curl -s https://api.adsb.lol/v2/mil | jq '.ac[0]'
```

## 2. Wire Up Observability

The template can run without external tracing, but you want Langfuse (or equivalent) early so every later step is measurable.

### Create a Langfuse project

1. Sign up at [cloud.langfuse.com](https://cloud.langfuse.com).
2. Create a project.
3. Under **Project Settings → API Keys**, create keys — you need a **public** key (`pk-lf-...`) and **secret** key (`sk-lf-...`).

### Configure and restart

Add to `packages/web-app/.env.local`:

```bash
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
# Optional — default is cloud; set explicitly if self-hosted or region-specific:
# LANGFUSE_BASE_URL=https://cloud.langfuse.com
```

Restart the stack (`Ctrl+C` then `pnpm dev:start`) so the web app picks up env vars.

### What traces show you

After a chat turn, open **Tracing** in Langfuse. You should see runs with tool spans (for example catalog and query tools), metadata such as tenant and provider, token counts, and latency breakdowns. Use that to confirm:

- The tool chain matches what you expect (catalog → query / semantic tools).
- Queries are reasonably selective.
- Cost and latency per step are visible for tuning later.

<Callout type="info" title="Redacted payloads">
The template may sanitize prompts and tool payloads before export (`trace-session` in `agent-runtime`). That is intentional for privacy; adjust locally if you need full text during development.
</Callout>

## 3. Get Your Data In

Replace the template’s demo model with your domain data, load it, and prove the agent queries the right table with the right tenant scope.

### How the template example is wired

Replacing `TenantKnowledge` touches more than one file. Typical layers:

| Layer            | Template example | You replace with |
| ---------------- | ---------------- | ---------------- |
| Data models      | `app/ingest/models.ts` | Your `OlapTable` / `Stream` / `IngestApi` |
| Semantic layer   | `app/semantic/knowledge.ts` | Query models for your tables (Step 4) |
| Dashboard        | `app/semantic/dashboard-snapshot.ts` | Metrics your UI needs |
| Contracts        | `packages/agent-contracts` | DTOs that match your API |
| Seed / scripts   | `seed/`, `scripts/seed.mjs` | Your seed or delete when fully live |
| Tests            | `test/*.test.ts` | Assertions on your models and tools |

Work in order: **model → ingest → verify in ClickHouse → semantic layer → clean up references** so you are never mid-migration longer than necessary.

### Collect a data sample

Before writing TypeScript, capture real field names, types, and values:

- **API** — Save a JSON response or point your coding agent at the endpoint.
- **File** — CSV / Parquet / JSON in repo or object storage.
- **Existing DB** — Export a few hundred rows or introspect schema.
- **ClickHouse `url()` / `s3()`** — `SELECT ... LIMIT 100` to inspect remote files.

<ToggleBlock openText="No data yet? Try a public dataset" closeText="Hide">
The [Amazon Customer Reviews](https://clickhouse.com/docs/getting-started/example-datasets/amazon-reviews) dataset is a large Parquet example you can query from ClickHouse without owning the raw files first.
</ToggleBlock>

**ADS-B sample** (one aircraft object from the military feed):

```bash
curl -s https://api.adsb.lol/v2/mil | jq '.ac[0]'
```

### Define your data model

The demo lives in `packages/moosestack-service/app/ingest/models.ts`. Add your domain model alongside or instead of `TenantKnowledge`, keeping **`tenant_id` and `SelectRowPolicy`** until you intentionally move to a public or single-tenant design.

Use the **ClickHouse best practices** skill (installed with the harness) for ordering keys, types, `LowCardinality`, and nullable rules. Reference patterns in the [aircraft-tracker example](https://github.com/514-labs/moosestack/tree/add-example-apps/examples/aircraft-tracker) for a full `OlapTable` + optional `Stream` / `IngestApi` setup.

### Clean up template references

After swapping models, fix imports and registrations — commonly:

- `app/index.ts` — export your tables / pipelines; remove stale re-exports.
- `app/mcp/tool-access/exposed-surface.ts` — should follow row policy; confirm your table is allowlisted.
- `app/semantic/knowledge.ts` and dashboard snapshot — stub or replace until Step 4.
- `app/mcp/server.ts` — you may temporarily comment semantic tool registration while the new model is incomplete.

Use MooseDev MCP (`get_infra_map`, `query_olap` / `DESCRIBE TABLE`) to confirm the new table exists and matches your intent.

### Load your data

Pick a strategy:

**One-shot / archive** — `INSERT ... SELECT` from `s3()`, `url()`, or a local file:

```bash
moose query "INSERT INTO your_table SELECT col_a, col_b FROM s3('https://...', 'Parquet')"
```

`moose query` reporting `0 rows` for an INSERT can be normal; follow with `SELECT COUNT(*)`.

**Scheduled / API polling** — Moose Workflow + ingest API. Example pattern:

```typescript
import { Task, Workflow } from "@514labs/moose-lib";

const pollTask = new Task<void, void>("poll-adsb", {
  run: async () => {
    const response = await fetch("https://api.adsb.lol/v2/mil");
    const body = await response.json();
    // Map `body.ac` to your model shape, then POST to your ingest API:
    // await fetch("http://localhost:4000/ingest/<path>", { method: "POST", body: JSON.stringify(rows) })
  },
  retries: 1,
  timeout: "30s",
});

export const adsbWorkflow = new Workflow("adsb-poll", {
  startingTask: pollTask,
  schedule: "@every 30s",
  retries: 1,
  timeout: "1m",
});
```

Export the workflow from `app/index.ts`. Adjust hostnames for production.

**Existing ClickHouse** — `moose db pull` to generate external models; `moose seed clickhouse` to copy sample rows locally.

**CDC / realtime** — ClickPipes or `IngestPipeline` + streaming; see [Performant dashboards — existing OLTP](/guides/applications/performant-dashboards/existing-oltp-db).

### Field mapping tips (APIs)

- Trim strings; normalize sentinel values (e.g. altitude `"ground"`).
- Align defaults with `ClickHouseDefault` in your schema.
- Add an ingestion timestamp (`polled_at`) when polling snapshots.

### Verify

```bash
moose ls
moose query "SELECT COUNT(*) FROM your_table"
moose peek your_table
```

In the chat UI, inspect tool results: queries should hit **your** table and include `tenant_id` filtering when RLS is enabled.

## 4. Build the Semantic Layer

The semantic layer declares **what questions are valid** — dimensions, metrics, and filters — once. The same `defineQueryModel` can back MCP tools, dashboard SQL, and REST handlers, so chat and dashboards do not drift.

### What to build

In `packages/moosestack-service/app/semantic/` (or your app’s convention), create models with:

- **Dimensions** — groupings (time buckets, categories, identifiers).
- **Metrics** — aggregations (`countIf`, averages, rates).
- **Filters** — safe knobs exposed to the agent.
- **Descriptions** — these strings are what the LLM reads when choosing tools; be explicit.

See `knowledge.ts` in the template for a worked `defineQueryModel` example, and the **aircraft-tracker** repo’s query-model files for a richer domain-specific set.

<Callout type="info" title="Use sql.fragment inside query models">
Prefer `sql.fragment` for expressions inside query models — bare `sql` may upset the LSP with “Invalid SQL” diagnostics.
</Callout>

### Wire into MCP

Register models in `app/mcp/server.ts` with `registerSemanticModelTools` / `registerModelTools` (exact API depends on your `moose-lib` version — follow the template’s imports). After registration, agents see typed tools instead of writing unconstrained SQL for those metrics.

### Verify: typed tools vs raw SQL

**Good** — The agent calls a named semantic tool with structured arguments (metrics, filters, time range). Easy to audit and consistent with dashboards.

**Bad** — The agent issues ad hoc `SELECT` for the same metric through `query_clickhouse` only. Harder to govern and easy to diverge from other surfaces.

Check Langfuse spans to confirm which tools fire after you ship the semantic layer.

## 5. Customize Your Agent

### Single agent vs multi-agent

The template may default to a **single-agent** stream with all tools attached — simpler latency and debugging. Consider **multi-agent** (supervisor → specialist → narrator) when:

- Tool sets or trust boundaries differ by role.
- Routing genuinely improves quality (specialists with different prompts).
- You want narrated polish separate from data gathering.

Multi-agent wiring lives in `packages/agent-runtime` (for example `create-multi-agent-stream.ts` and `prompts/multi-agent.ts`); the Next adapter is `packages/web-app/src/lib/chat-agent.ts`. For design tradeoffs, see Anthropic’s [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents).

### System prompt

Edit `packages/agent-runtime/src/prompts/default-system.ts` (`DEFAULT_AGENT_SYSTEM_PROMPT`). Describe:

- What data exists and what each key field means.
- How you want answers formatted and how metrics should be named.
- Domain rules (for an ADS-B-style app: squawk codes, altitude bands, what counts as an anomaly).

### Optional: domain specialist

Add prompts and supervisor routing in `packages/agent-runtime/src/prompts/multi-agent.ts`. The narrator consumes specialist output; MCP and web wiring usually stay the same.

### Optional: custom MCP tool

Add a registrar under `packages/moosestack-service/app/mcp/tools/` and call it from `app/mcp/server.ts`. Use readonly execution helpers so row policies stay enforced:

```typescript
import type { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { z } from "zod/v3";
import { executeReadonlyStatement } from "../../data/clickhouse/readonly-query";
import type { TenantMooseContext } from "../../http/context/tenant-context";

export function registerMyTool(
  server: McpServer,
  context: Pick<TenantMooseContext, "moose" | "rowPolicyOptions">,
): void {
  server.registerTool(
    "my_tool",
    {
      title: "Human-readable title",
      description: "Be specific — the agent reads this to decide when to use the tool.",
      inputSchema: {
        param: z.string().describe("What this parameter controls"),
      },
    },
    async ({ param }) => {
      const { client } = context.moose;
      const rows = await executeReadonlyStatement(client.query, `SELECT ...`, {
        limit: 100,
        rowPolicyOptions: context.rowPolicyOptions,
      });
      return {
        content: [{ type: "text" as const, text: JSON.stringify(rows, null, 2) }],
      };
    },
  );
}
```

Return structured errors with `{ isError: true }` when appropriate instead of throwing uncaught exceptions.

### Rebuild gotcha

Changes under `packages/agent-runtime/` (and shared packages) are not always picked up by the Next dev server alone. After prompt or stream changes:

```bash
pnpm --filter agent-runtime build
```

Then restart `pnpm dev:web` or the full `pnpm dev:start` stack.

## 6. Build Your Frontend (optional)

The template ships a working Next.js app under `packages/web-app/`. You can **customize** it or **replace** it.

### Customize the template UI

Typical touch points:

- `src/app/page.tsx` — dashboard cards (replace “knowledge” metrics with yours).
- Chat suggested prompts — align with your domain vocabulary.
- Marketing / landing copy — describe your product, not the generic template.

The two-tenant picker demonstrates RLS; for public data you might collapse to one tenant or keep the machinery and ignore the extra tenant.

### Build from scratch

If you bring your own frontend, wire:

- `MOOSE_SERVICE_URL` — base URL for your MooseStack service.
- Auth — align JWT / OIDC with how the service resolves `tenant_id` and row policies.
- Chat transport — whatever endpoint your `chat-agent` adapter exposes (mirror the template’s API routes).

Use the template `web-app` as a reference for env vars and request shapes.

## 7. Harden for Production

### Observability tuning

Use Langfuse to ask:

- Are scans broader than expected? Promote hot aggregates to materialized views ([Materialized views](/moosestack/materialized-views?lang=typescript)).
- Where is latency and token spend going per tool / model step?
- Do traces reflect renamed specialists or custom metadata you care about?

### Semantic consistency

If chat still bypasses semantic tools for common questions, tighten prompts or remove redundant escape hatches. Dashboards and APIs should call the same query models you registered for MCP.

### Row-level security

Confirm every domain table appears in your `SelectRowPolicy` when tenants must be isolated. Validate by signing in as different tenants and inspecting SQL in traces — `WHERE tenant_id = ...` should come from enforced policies, not luck.

Public or single-tenant apps (like raw ADS-B) may simplify or drop row policies **intentionally**; keep JWT plumbing consistent with how you issue tokens.

### Guardrails

Managed guardrails in this template are centered on **AWS Bedrock** (`BEDROCK_GUARDRAIL_ID` / version in `.env.local`). Other providers often use pass-through adapters; plan custom assessment (`GuardrailAdapter`) if you need parity.

### Before committing

```bash
pnpm build
pnpm build:service
pnpm test
pnpm lint
pnpm format
```

(Add or swap scripts to match your repo’s package scripts.)

## 8. Deploy

### MooseStack service (514 hosting)

1. Open [boreal.cloud](https://boreal.cloud), create a project, connect GitHub, set the service root to `packages/moosestack-service`.
2. Set production env vars: AI provider keys, Langfuse keys, optional Bedrock guardrail IDs, and `MOOSE_JWT__SECRET` (production OIDC public key material as required by your setup).
3. Push `main` to deploy; open PRs for preview environments with isolated ClickHouse where configured.

For production OIDC (replacing mock auth):

- Set `MOOSE_AUTH_MODE=oidc` and OIDC client variables in the **web** app.
- Align `[jwt]` issuer and audience in `packages/moosestack-service/moose.config.toml` with your IdP.

### Web app (Vercel)

The template’s `vercel.json` documents required variables. Connect the repo, point Vercel at `packages/web-app` if needed, and set at minimum:

- `AUTH_SECRET`
- `MOOSE_SERVICE_URL`
- AI provider variables
- Langfuse / Bedrock / OIDC as applicable

Smoke-test chat in production and confirm a trace lands in Langfuse with correct tenant metadata.
