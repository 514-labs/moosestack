# Optimizing ClickHouse Performance with AI

Use this guide when a ClickHouse query is slow and you want the `514` agent harness to run an end-to-end optimization workflow. The agent does not just make one guess. It profiles the production query path, proposes one or more candidate schema changes, freezes a `perf/baseline` branch, wires the same benchmark target across branches, benchmarks each candidate against that baseline, and opens a PR for the winning branch. Because the baseline and candidate branches share the same query contract and comparable preview data, you can review the result like a controlled experiment instead of a one-off claim.

Your role is to make sure the CLI and agent harness are set up in your environment, approve raw ClickHouse queries when prompted, and review the winning branch at the end. The artifacts that matter for that review are the scaffolded `query-benchmarks/` package, the baseline benchmark report, the winning candidate benchmark report, and a reviewable `migrations/plan.yaml` so you can confirm the schema change is safe to merge and will not accidentally ship an unintended database change.

<Callout type="info" title="What success looks like">
- A scaffolded `query-benchmarks/` package that exercises the real production query path
- A frozen baseline branch and one or more candidate branches compared with the same test
- A PR for the winning candidate with benchmark evidence and a reviewed `migrations/plan.yaml`
</Callout>

This guide assumes:

- Your MooseStack app is already deployed on Fiveonefour
- The agent can either reuse an existing query path in code or define a query model when profiling uncovers a production pattern without one

### Optimization workflow

**This section gets the 514 harness set up with your coding agent and runs the optimization workflow.** After `514 agent init`, the workflow uses the `514` CLI to inspect ClickHouse metrics and logs, profile the slow path, scaffold a benchmark package with `moose add benchmark`, propose candidate fixes based on what it actually sees, freeze a control branch, and benchmark candidate branches against it. Part of that run is wiring a benchmark target that stays the same across baseline and candidate branches. The point is not to prove that one preview database is faster. The point is to compare the same query path across a control and one or more candidates, then ship the winner.

Watch three things as it runs:

- **The harness is active:** `514 agent init` succeeds and the skills and MCP wiring match your setup.
- **The profiling target is clear:** name the slow query or endpoint and confirm the perf skill, not a generic refactor.
- **The experiment path is visible:** proposed candidates, the frozen baseline, candidate branches, raw SQL, and any re-seed caused by `ORDER BY` or table layout changes should all be explicit.

<GuideStepper.Checkpoint title="Expect seven internal stages">
The workflow follows `SETUP → PROFILE → PROPOSE → BASELINE → EXPERIMENT → COMPARE → SHIP`.

- **SETUP:** CLI session, project, deployment, baseline DDL.
- **PROFILE:** Slow queries, `EXPLAIN`, storage diagnostics, and the benchmark query set.
- **PROPOSE:** Candidate schema changes, risks, and re-seed categories.
- **BASELINE:** Benchmark scaffold, target interface, frozen `perf/baseline`, and a proven control run.
- **EXPERIMENT:** Candidate branches, preview deploys, re-seeds if needed, and benchmark runs.
- **COMPARE:** Baseline versus candidates, regressions, and winner selection.
- **SHIP:** PR for the winning candidate with evidence and summary.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Know what the benchmark scaffold creates">
The workflow should run `moose add benchmark` and reuse the generated package instead of hand-writing benchmark infrastructure. In the prototype, that scaffold looks like this:

```text
query-benchmarks/
  benchmark.config.ts
  benchmark/core.ts
  tests/query-benchmarks.test.ts
  package.json
```

Treat that package as part of the review surface. `benchmark.config.ts` is where the benchmark target, scenarios, thresholds, and sampling live. `tests/query-benchmarks.test.ts` is the generated runner that executes the contract and writes the reports.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Understand the benchmark target contract">
The benchmark target interface is the code-level representation of the production query pattern the agent discovered. It can be an existing `defineQueryModel`, an existing query builder, or a new query model the agent creates if profiling finds a real query pattern without a codified entrypoint.

What should stay the same across baseline and candidate branches:

- the same base query or API entrypoint
- the same scenarios and filters
- the same thresholds and sampling
- the same query shape apart from the intended optimization

What is allowed to change per candidate branch:

- the minimal table or model reference needed to point at the optimized layout

Example:

```ts
const baseQuery = () => buildQuery(benchmarkModel);

export const benchmark = defineBenchmark({
  baseQuery,
  scenarios: [
    {
      name: "category=A3",
      query: () => baseQuery().filter("category", "eq", "A3"),
    },
  ],
  thresholds: {
    baselineP95Ms: 500,
    scenarioRegressionRatio: 2.5,
  },
});
```

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Approve gated ClickHouse commands">
The `514 agent ...` workflow is guardrailed, so its built-in steps run without extra approval. Raw `514 clickhouse query` (DDL, `EXPLAIN`, diagnostics, re-seed) should prompt you. Approve when the SQL matches intent.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Watch for candidate re-seeds">
If `ORDER BY` or similar forces a rebuild, each candidate branch may need a re-seed before benchmarks are trustworthy. The PR should say which candidate needed it and how the data was copied forward.

</GuideStepper.Checkpoint>

<Callout type="info" title="What good evidence looks like">
Example: index use, fewer granules read (for example selective condition vs full scan, high `granuleSkipPct`), lower server-side latency. Your PR should show that kind of structural move in `EXPLAIN`, not only a headline number.
</Callout>
</GuideStepper.Step>
</GuideStepper>

### PR review

**This is the part that matters.** The agent can open a PR. You still decide what ships. Your job here is to check that the change is safe and that the evidence matches reality.

- **Performance:** Do benchmarks and `EXPLAIN` back the claim, not just the PR text?
- **Destructive ops:** Does `ORDER BY` or ordering change imply a rebuild you accept? Read `migrations/plan.yaml` with that in mind.

**Read `migrations/plan.yaml` end to end.** If `ORDER BY` or a rebuild is involved, expect a **backfill** or migration path, not only a new table. Keep the **old table** until the new one is safe. Populate and verify before drop or rename.

Order: benchmarks, then plan and diff, then optional reruns.

Read `tests.filterRegression`. It is an object keyed by variant name, not a status array. Compare `ratio` against the `2.5` threshold yourself.


<GuideStepper.Checkpoint title="Find the new versioned table in the diff">
In the diff, the optimized layout should appear as a new **`OlapTable` version**; leave the old version unchanged. For example:

```diff
 export const UserEventsV1 = new OlapTable("UserEvents", {
   version: "1.0",
   orderByFields: ["timestamp", "current_database"],
 });

+export const UserEventsV2 = new OlapTable("UserEvents", {
+  version: "2.0",
+  orderByFields: ["current_database", "timestamp"],
+});
```

Validate: **bumped `version`** on the new definition, previous version unchanged. Storage change with no new `version` on `OlapTable` needs an explanation.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Confirm the benchmark reads from the new model">
The benchmark should read the **new versioned table**, not the old one. Expect a small diff:

```diff
-import { UserEventsV1 } from "./models";
+import { UserEventsV2 } from "./models";

 const query = sql`
   SELECT count()
-  FROM ${UserEventsV1}
+  FROM ${UserEventsV2}
   WHERE timestamp >= ${start}
 `;
```

Schema, benchmark, and claim should line up. If the summary promises better skipping on `current_database` but the benchmark still hits the old table or the diff is unrelated noise, ask before merge.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Open migrations/plan.yaml and match the plan shape">
Open `migrations/plan.yaml`. Operations should match the versioned table change in code. Flag unexpected `DropTable` or `DropTableColumn`. Re-seeds need a note in the PR. See [Planned Migrations](/moosestack/migrate/planned-migrations).

Staged rollout shape:

```yaml
operations:
  - CreateTable:
      name: UserEvents_2_0
      columns: ...
      orderBy: [current_database, timestamp]
  - RawSql:
      sql: |
        INSERT INTO UserEvents_2_0
        SELECT *
        FROM UserEvents_1_0
```

Create table, then backfill. No destructive lifecycle in this PR. Code shows `version: "2.0"` but the plan has no new table plus copy? Ask why.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Validate the backfill and keep the old table">
`ORDER BY` or a rebuild needs a **backfill** in the plan, not only `CreateTable`. Usually a late **`RawSql`** `INSERT INTO <new> SELECT ... FROM <old>`.

Good shape:

```yaml {5-9}
operations:
  - CreateTable:
      name: UserEvents_2_0
      orderBy: [current_database, timestamp]
  - RawSql:
      sql: |
        INSERT INTO UserEvents_2_0
        SELECT *
        FROM UserEvents_1_0
```

New table with no backfill or `RawSql` copy? Request changes.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Look for unexpected DropTable operations">
**Do not drop the old table in the optimization PR.** Keep it as fallback until the new layout is validated.

Bad shape:

```yaml {5-6}
operations:
  - CreateTable:
      name: UserEvents_2_0
      orderBy: [current_database, timestamp]
  - DropTable:
      name: UserEvents_1_0
```

Early `DropTable` on the old table? Fix the plan before merge.

Removing `events_old` or other fallbacks belongs in a **follow-up PR**, not this one.

</GuideStepper.Checkpoint>
</GuideStepper.Step>

<GuideStepper.Checkpoint title="Find the database names for the baseline and winning candidate forks">
Between the baseline preview fork and the winning candidate preview fork, the ClickHouse **host**, **port**, **user**, **password**, and **SSL setting** are the same. They share one 514-hosted ClickHouse cluster. The only value that changes is the **database name**.

Use `514 agent deployment list` to list the agent-visible deployments for the project and find the database names for each branch. See [`514 agent`](/hosting/cli/agent) for command context.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Create a shared .env.remote file">
The `.env.remote` file should contain the shared connection settings **plus** your default database name. Use the baseline preview fork as the default so your first rerun is the unchanged comparison target:

```bash
MOOSE_CLICKHOUSE_CONFIG__HOST=<your-cluster>.clickhouse.boreal.cloud
MOOSE_CLICKHOUSE_CONFIG__HOST_PORT=8443
MOOSE_CLICKHOUSE_CONFIG__USER=default
MOOSE_CLICKHOUSE_CONFIG__PASSWORD=<your-password>
MOOSE_CLICKHOUSE_CONFIG__DB_NAME=<baseline-preview-db-name>
MOOSE_CLICKHOUSE_CONFIG__USE_SSL=true
```

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Swap only the database name between runs">
Then swap only the database name between runs:

```bash

# Test against winning candidate preview fork
MOOSE_CLICKHOUSE_CONFIG__DB_NAME=<winning-candidate-preview-db-name> pnpm test:perf
```

</GuideStepper.Checkpoint>

## Benchmark JSON quick reference

Use this when you need the full field map while reviewing the benchmark step above.

```json
{
  "timestamp": "2026-03-23T18:12:00.000Z",
  "target": {
    "host": "cluster.clickhouse.boreal.cloud",
    "database": "514-demos-planes-perf-base-59be4"
  },
  "tests": {
    "baseline": {
      "sql": "SELECT ...",
      "p50": 38,
      "p95": 44,
      "profiles": [{ "durationMs": 42 }]
    },
    "filterRegression": {
      "category=A3": { "p50": 24, "p95": 31, "baselineP95": 29, "ratio": 1.07 }
    },
    "explainCategoryFilter": {
      "sql": "SELECT ...",
      "explain": { "indexCondition": "..." }
    },
    "concurrentBurst": { "concurrency": 10, "errors": 0 },
    "clusterState": {},
    "connectionDiagnostics": {}
  }
}
```

`target` tells you which database ran the test. `tests.*` holds the evidence you compare.

| What to compare    | Where in the report                                  | What good looks like              |
| ------------------ | ---------------------------------------------------- | --------------------------------- |
| Index used?        | `tests.explainCategoryFilter.explain.indexCondition` | Not `"true"`                      |
| Granules skipped?  | `tests.explainCategoryFilter.explain.granuleSkipPct` | Higher in optimized than baseline |
