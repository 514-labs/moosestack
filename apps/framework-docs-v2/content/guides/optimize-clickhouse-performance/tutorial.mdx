# Optimizing ClickHouse Performance with AI

**Setup** points the CLI, auth, and repo link at the right Fiveonefour project. **Optimization workflow** runs the agent harness: profile, preview, PR with proof. **PR review** is where you decide if the evidence and `migrations/plan.yaml` are good enough to ship.

You may approve raw `514 clickhouse query` during the run. Before merge, review benchmark artifacts and `migrations/plan.yaml`, not only the agent summary.

<Callout type="info" title="What success looks like">
  - A PR with schema changes and committed benchmark artifacts - Preview
  deployment with the optimized path benchmarked - A reviewed
  `migrations/plan.yaml` that matches what you intend to ship
</Callout>

This guide assumes:

- Your MooseStack app is already deployed on Fiveonefour
- The query path you want to optimize already exists in code, usually as `sql` or `defineQueryModel` / `buildQuery`

### Setup

**Setup** is what keeps the rest honest: real `514` commands against the right Fiveonefour project, and the agent using the same session and link. Wrong context means failed runs or the wrong deployment.

You need: working `514 --version`, `514 auth whoami` for the right org, and `514 link` (or [`514 project link`](/hosting/cli/projects/link)) from the repo root to the correct `org/project`.

Order: install, sign in, link.

### Optimization workflow

**This section sets up the agent harness in your copilot and gets your coding agent to run the optimization workflow.** After `514 agent init`, the workflow uses the `514` CLI to inspect ClickHouse query metrics and logs, profile the slow path, and propose optimization fixes grounded in what it finds. Part of that workflow is having the agent create a **Vitest benchmark test** for the optimized path. That test produces a real benchmark report you review at the end of the run, not just an agent summary. The same Vitest test is designed to run against the preview database and the `main` / production database so you can make a fair before-and-after comparison.

Watch three things as it runs:

- **The harness is active:** `514 agent init` succeeds and the skills and MCP wiring match your setup.
- **The profiling target is clear:** name the slow query or endpoint and confirm the perf skill, not a generic refactor.
- **The validation path is visible:** raw SQL, preview deploys, and any re-seed caused by `ORDER BY` or table layout changes should all be explicit.

<GuideStepper.Checkpoint title="Expect five internal stages">
The workflow follows `SETUP → PROFILE → OPTIMIZE → VERIFY → SHIP`.

- **SETUP:** CLI session, project, deployment, baseline DDL.
- **PROFILE:** Slow queries, benchmark candidates, baseline `EXPLAIN`, re-seed risk.
- **OPTIMIZE:** Moose models, branch push, preview.
- **VERIFY:** Schema diff, `EXPLAIN`, storage, timed runs on preview.
- **SHIP:** PR with evidence and summary.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Approve gated ClickHouse commands">
Guardrailed `514 agent ...` runs without extra approval. Raw `514 clickhouse query` (DDL, `EXPLAIN`, diagnostics, re-seed) should prompt you. Approve when the SQL matches intent.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Watch for preview re-seeds">
If `ORDER BY` or similar forces a rebuild, preview may need a re-seed before benchmarks are trustworthy. The PR should say if that happened.

</GuideStepper.Checkpoint>

<Callout type="info" title="What good evidence looks like">
Example: index use, fewer granules read (for example selective condition vs full scan, high `granuleSkipPct`), lower server-side latency. Your PR should show that kind of structural move in `EXPLAIN`, not only a headline number.
</Callout>
</GuideStepper.Step>
</GuideStepper>

### PR review

**Human review of the agent's work.** You decide what ships. Check that the change is safe and the evidence matches reality.

- **Performance:** Do benchmarks and `EXPLAIN` back the claim, not just the PR text?
- **Destructive ops:** Does `ORDER BY` or ordering change imply a rebuild you accept? Read `migrations/plan.yaml` with that in mind.

**Read `migrations/plan.yaml` end to end.** If `ORDER BY` or a rebuild is involved, expect a **backfill** or migration path, not only a new table. Keep the **old table** until the new one is safe. Populate and verify before drop or rename.

Order: benchmarks, then plan and diff, then optional reruns.

<GuideStepper.Checkpoint title="Read the report structure first">
Before you compare anything, get oriented in the JSON. The useful keys are at the top level:

```json
{
  "timestamp": "2026-03-23T18:12:00.000Z",
  "target": {
    "host": "cluster.clickhouse.boreal.cloud",
    "database": "514-demos-planes-main-59be4"
  },
  "tests": {
    "baseline": {
      "sql": "SELECT ...",
      "p50": 38,
      "p95": 44,
      "profiles": [{ "durationMs": 42 }]
    },
    "filterRegression": {
      "category=A3": { "p50": 24, "p95": 31, "baselineP95": 29, "ratio": 1.07 }
    },
    "explainCategoryFilter": {
      "sql": "SELECT ...",
      "explain": { "indexCondition": "..." }
    },
    "concurrentBurst": { "concurrency": 10, "errors": 0 },
    "clusterState": {},
    "connectionDiagnostics": {}
  }
}
```

`target` tells you which database ran the test. `tests.*` holds the evidence you compare.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Use this comparison checklist">
Open the optimized and baseline reports side by side and work down this list:

| What to compare    | Where in the report                                  | What good looks like              |
| ------------------ | ---------------------------------------------------- | --------------------------------- |
| Index used?        | `tests.explainCategoryFilter.explain.indexCondition` | Not `"true"`                      |
| Granules skipped?  | `tests.explainCategoryFilter.explain.granuleSkipPct` | Higher in optimized than baseline |
| Server-side p95?   | `tests.baseline.p95`                                 | Lower in optimized than baseline  |
| Rows read?         | `tests.baseline.profiles[0].readRows`                | Lower in optimized                |
| Memory usage?      | `tests.baseline.profiles[0].memoryUsage`             | Lower in optimized                |
| Filter regression? | `tests.filterRegression.<variant>.ratio`             | Below `2.5`                       |
| Correctness?       | Separate correctness report                          | `match: true`                     |

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Check for a real index condition">
In `reports/benchmark-details-*.json`, check `tests.explainCategoryFilter.explain.indexCondition`. If index use is the goal, it should not be only `"true"`.

```json
{
  "tests": {
    "explainCategoryFilter": {
      "explain": {
        "indexCondition": "and((current_database in ['db_123']), (timestamp >= 1710200000))"
      }
    }
  }
}
```

`"true"` usually means no selective index condition:

```json
{
  "tests": {
    "explainCategoryFilter": {
      "explain": {
        "indexCondition": "true"
      }
    }
  }
}
```

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Check filter regression ratios">
Read `tests.filterRegression`. It is an object keyed by variant name, not a status array. Compare `ratio` against the `2.5` threshold yourself.

```json
{
  "tests": {
    "filterRegression": {
      "category=A3": { "p50": 24, "p95": 31, "baselineP95": 29, "ratio": 1.07 },
      "altitude range": {
        "p50": 26,
        "p95": 33,
        "baselineP95": 28,
        "ratio": 1.18
      }
    }
  }
}
```

Below `2.5` means the variant did not regress beyond the threshold. If a ratio is above `2.5`, the PR should explain why.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Verify the SQL matches your app code">
Use the `sql` field in each test entry to confirm the report executed the query path the PR claims to optimize. For example:

```json
{
  "tests": {
    "baseline": {
      "sql": "SELECT current_database, count() FROM ..."
    }
  }
}
```

If that SQL does not match the app code or benchmark target in the PR, stop and ask why.

</GuideStepper.Checkpoint>

  number={2}
  title="Review the migration plan and the code changes"
  summary="Read migrations/plan.yaml and the diff so you know exactly what will change in ClickHouse."
>
<GuideStepper.WhatYouNeed>
- The same PR
- Comfort reading `migrations/plan.yaml` and TypeScript data model diffs
</GuideStepper.WhatYouNeed>
<GuideStepper.WhatYouGet>
- A clear picture of schema operations (and app code changes) before they hit production
</GuideStepper.WhatYouGet>

<GuideStepper.Checkpoint title="Find the new versioned table in the diff">
In the diff, the optimized layout should appear as a new **`OlapTable` version**; leave the old version unchanged. For example:

```diff
 export const UserEventsV1 = new OlapTable("UserEvents", {
   version: "1.0",
   orderByFields: ["timestamp", "current_database"],
 });

+export const UserEventsV2 = new OlapTable("UserEvents", {
+  version: "2.0",
+  orderByFields: ["current_database", "timestamp"],
+});
```

Validate: **bumped `version`** on the new definition, previous version unchanged. Storage change with no new `version` on `OlapTable` needs an explanation.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Confirm the benchmark reads from the new model">
The benchmark should read the **new versioned table**, not the old one. Expect a small diff:

```diff
-import { UserEventsV1 } from "./models";
+import { UserEventsV2 } from "./models";

 const query = sql`
   SELECT count()
-  FROM ${UserEventsV1}
+  FROM ${UserEventsV2}
   WHERE timestamp >= ${start}
 `;
```

Schema, benchmark, and claim should line up. If the summary promises better skipping on `current_database` but the benchmark still hits the old table or the diff is unrelated noise, ask before merge.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Open migrations/plan.yaml and match the plan shape">
Open `migrations/plan.yaml`. Operations should match the versioned table change in code. Flag unexpected `DropTable` or `DropTableColumn`. Re-seeds need a note in the PR. See [Planned Migrations](/moosestack/migrate/planned-migrations).

Staged rollout shape:

```yaml
operations:
  - CreateTable:
      name: UserEvents_2_0
      columns: ...
      orderBy: [current_database, timestamp]
  - RawSql:
      sql: |
        INSERT INTO UserEvents_2_0
        SELECT *
        FROM UserEvents_1_0
```

Create table, then backfill. No destructive lifecycle in this PR. Code shows `version: "2.0"` but the plan has no new table plus copy? Ask why.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Validate the backfill and keep the old table">
`ORDER BY` or a rebuild needs a **backfill** in the plan, not only `CreateTable`. Usually a late **`RawSql`** `INSERT INTO <new> SELECT ... FROM <old>`.

Good shape:

```yaml {5-9}
operations:
  - CreateTable:
      name: UserEvents_2_0
      orderBy: [current_database, timestamp]
  - RawSql:
      sql: |
        INSERT INTO UserEvents_2_0
        SELECT *
        FROM UserEvents_1_0
```

New table with no backfill or `RawSql` copy? Request changes.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Look for unexpected DropTable operations">
**Do not drop the old table in the optimization PR.** Keep it as fallback until the new layout is validated.

Bad shape:

```yaml {5-6}
operations:
  - CreateTable:
      name: UserEvents_2_0
      orderBy: [current_database, timestamp]
  - DropTable:
      name: UserEvents_1_0
```

Early `DropTable` on the old table? Fix the plan before merge.

Removing `events_old` or other fallbacks belongs in a **follow-up PR**, not this one.

</GuideStepper.Checkpoint>
</GuideStepper.Step>

<GuideStepper.Checkpoint title="Point tests at preview, then at main">
The optimization workflow should leave you with a **Vitest** benchmark and helper scripts for rerunning it. Use that same benchmark and only change the target database.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Find the database names for baseline and optimized preview">
Between optimized preview and baseline `main`, the ClickHouse **host**, **port**, **user**, **password**, and **SSL setting** are the same. They share one 514-hosted ClickHouse cluster. The only value that changes is the **database name**.

Use `514 agent deployment list` to find the database names for each branch.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Create a shared .env.remote file">
The `.env.remote` file should contain the shared connection settings **plus** your default database name (here we use `main` / production):

```bash
MOOSE_CLICKHOUSE_CONFIG__HOST=<your-cluster>.clickhouse.boreal.cloud
MOOSE_CLICKHOUSE_CONFIG__HOST_PORT=8443
MOOSE_CLICKHOUSE_CONFIG__USER=default
MOOSE_CLICKHOUSE_CONFIG__PASSWORD=<your-password>
MOOSE_CLICKHOUSE_CONFIG__DB_NAME=<main-db-name>
MOOSE_CLICKHOUSE_CONFIG__USE_SSL=true
```

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Swap only the database name between runs">
Then swap only the database name between runs:

```bash
# Test against baseline (uses DB_NAME from .env.remote)
pnpm test:perf

# Test against optimized preview
MOOSE_CLICKHOUSE_CONFIG__DB_NAME=<preview-db-name> pnpm test:perf
```

</GuideStepper.Checkpoint>
</GuideStepper.Step>
