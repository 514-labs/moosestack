# Optimize a Slow ClickHouse Query with Your AI Agent

Use this guide when a production ClickHouse query in your MooseStack app is slower than it should be.

You will set up your AI coding agent with the `514` harness to benchmark the slow query against one or more optimized candidates. By the end you will have a reviewable PR with the winning schema changes and benchmark evidence.

The experiment:

1. Profiles the slow query and proposes optimization candidates
2. Creates isolated preview databases on 514 hosting for the baseline and each candidate
3. Benchmarks every preview with the same test to pick the best performer
4. Opens a PR for the winner for your review

This guide assumes:

- MooseStack version **0.6.493** or later (run `npx moose-cli --version` or `moose --version` to check)
- Your MooseStack app is already deployed on Fiveonefour
- Your coding agent is open on this repository
- The agent can reuse an existing query path or define a query model when profiling finds a pattern without one

## Optimization workflow

This section helps you understand what the agent is doing at each stage of the optimization workflow, what it may ask you to confirm, and how to spot issues early enough to unblock the run.

You can use this workflow whether you already know which query needs work or need the agent to help identify a good optimization target first. It verifies the setup, runs the optimization workflow in preview branch databases, and leaves production untouched. The end result is a PR with the evidence you need to decide whether the change is ready to move forward.

Even if a candidate involves a destructive change like dropping and recreating a table, or a rebuild triggered by reordering the `ORDER BY`, all of that happens on an isolated preview database. Your production database is not touched at any point during this workflow. The only path to production is the pull request you review at the end.

<GuideStepper.WhatYouNeed>
- The candidate plan approved

<GuideStepper.Checkpoint title="Confirm the agent created the baseline branch">
The agent should create and push a `perf/baseline` branch with your current schema unchanged. Once pushed, go to your Fiveonefour hosting deployments page and check that a new build appears in the deployments list for the `perf/baseline` branch. That deployment is the frozen control every candidate will be compared against.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Confirm the benchmark package was scaffolded">
The agent should run `moose add benchmark --dir ../query-benchmarks` to scaffold the benchmark package as a sibling to your MooseStack project. Confirm the structure matches:

```text
parent-directory/
├── your-moosestack-project/
│   └── ...
└── query-benchmarks/
    ├── benchmark.config.ts
    ├── benchmark/
    │   └── core.ts
    ├── tests/
    │   └── query-benchmarks.test.ts
    └── package.json
```

`benchmark.config.ts` defines the benchmark contract. `tests/query-benchmarks.test.ts` runs it and writes reports. Both are part of the review surface later.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Confirm your MooseStack project is a dependency of the benchmark package">
The agent should add your MooseStack project as a package dependency in the benchmark package's `package.json`. This is what lets the benchmark config import your Moose-defined queries directly.

Check that your MooseStack project appears in `dependencies`. You should see something like this in the benchmark package's `package.json`:

```json filename="query-benchmarks/package.json"
{
  "dependencies": {
    "your-moosestack-project": "workspace:*"
  }
}
```

If the import fails to resolve after this is in place, run `pnpm install` from the benchmark package directory.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Confirm the correct query was imported into the benchmark config">
The agent should import the slow query the workflow profiled earlier into `benchmark.config.ts`. This is the query every preview database will be benchmarked against. It can be an existing `defineQueryModel`, a query builder, or a new query model the agent creates if profiling found a pattern without a codified entrypoint.

Check that the query in `benchmark.config.ts` matches the slow path from the profiling step.

What should stay the same across baseline and candidate branches:

- the same base query or API entrypoint
- the same scenarios and filters
- the same thresholds and sampling
- the same query shape apart from the intended optimization

What is allowed to change per candidate branch:

- the minimal table or model reference needed to point at the optimized layout

Example:

```ts filename="query-benchmarks/benchmark.config.ts"
import { benchmarkModel } from "your-moosestack-project";
import { buildQuery, defineBenchmark } from "@514labs/moose-lib";

const baseQuery = () => buildQuery(benchmarkModel);

export const benchmark = defineBenchmark({
  baseQuery,
  scenarios: [
    {
      name: "category=A3",
      query: () => baseQuery().filter("category", "eq", "A3"),
    },
  ],
  thresholds: {
    baselineP95Ms: 500,
    scenarioRegressionRatio: 2.5,
  },
});
```

</GuideStepper.Checkpoint>
</GuideStepper.Step>

```bash

```

This writes the ClickHouse host, user, password, database name, and SSL setting for the current branch's preview deployment into `.env.local`. Run it from inside the generated benchmark package directory for the branch you want to test.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Watch for candidate re-seeds">
If `ORDER BY` or similar forces a rebuild, each candidate branch may need a re-seed before benchmarks are trustworthy. The PR should say which candidate needed it and how the data was copied forward.

</GuideStepper.Checkpoint>
</GuideStepper.Step>

<GuideStepper.Checkpoint title="Watch the agent present its findings">
Once all candidate benchmarks are done, the agent compares latency, `EXPLAIN` output, rows read, and memory usage across every candidate and the frozen baseline. It picks the best performer and presents its reasoning.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Review the summary table">
The agent should show a summary table comparing benchmark numbers for each candidate versus the baseline. Check that there is a clear winner, and note any scenarios that were skipped, flat, or regressed.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Weigh in on tradeoffs if needed">
If two candidates are close, the agent may ask which tradeoff you prefer (for example, one is faster on filtered queries but slower on full scans). If all candidates are flat or worse than the baseline, you may want to propose a different optimization direction or stop here. If a candidate regressed on some scenarios but improved on others, decide whether the improvement is worth the tradeoff.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Let the agent open the PR">
The agent may ask whether you want it to open a pull request for the winning candidate. Confirm that you do. Once the PR is created, click the link the agent gives you. </GuideStepper.Checkpoint>

## PR review

**The experiment is over. The PR is now the review surface.** The agent can open a PR, but you still decide what ships.

You should confirm two things here:

- the benchmarks and `EXPLAIN` support the performance claim
- any rebuild, backfill, or destructive step is explicit and acceptable before production

<GuideStepper id="optimize-ch-pr" persist>
<GuideStepper.Step
  id="review-benchmark-results"
  number={1}
  title="Review the benchmark results"
  summary="Read the benchmark package and benchmark JSON to verify the evidence in the PR."
>
<GuideStepper.WhatYouNeed>
- The PR the agent opened
- The committed `query-benchmarks/` package
- The benchmark artifacts for both the frozen baseline branch and the winning candidate branch:
  - `reports/test-results.json`
  - `reports/benchmark-*.json`
</GuideStepper.WhatYouNeed>
<GuideStepper.WhatYouGet>
- Confidence that the winning candidate branch actually beats the baseline for the same query path, without hiding a scenario-level regression
</GuideStepper.WhatYouGet>

<GuideStepper.Checkpoint title="Start with the PR summary, then open the JSON files">
The agent should summarize the JSON results in the PR description, often as a small comparison table. Use that summary to orient yourself, but do not treat it as the evidence.

The evidence lives in the JSON files:

- `test-results.json` tells you which benchmark assertions passed, failed, or were skipped
- `benchmark-*.json` contains the detailed benchmark evidence for a specific target database

You should always be able to trace a PR claim back to one of those two files.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Identify the winner report and the baseline report">
Pair two artifact sets: **winner** (the candidate branch the agent selected) and **baseline** (the frozen control branch with no schema change). The timestamped benchmark report usually does not include a branch field. In practice, the **database name contains the branch slug**, so that is the field to inspect first.

Both runs must use the **same benchmark package** and query path contract, different targets only. No clear baseline means no real before/after.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Read the scaffolded benchmark package">
Open the committed benchmark package, usually `query-benchmarks/`. Start with `query-benchmarks/benchmark.config.ts`, then read `query-benchmarks/tests/query-benchmarks.test.ts`.

What to confirm before you trust any report:

- `benchmark.config.ts` points at the real query target the PR claims to optimize
- `baseQuery`, scenarios, thresholds, and sampling are the same between baseline and winner
- the generated test runner is still exercising that same contract
- only the minimal target change was introduced for the winner, usually a table or model reference

If the benchmark package changed in broader ways than that, the comparison is no longer clean.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Open test-results.json first">
Use `test-results.json` as the verdict file. It tells you:

- whether the run succeeded overall
- which benchmark assertions passed, failed, or were skipped
- the exact failing assertion when something broke

In the current benchmark package, that usually means:

- `baseline p95 under threshold`
- `scenarios do not regress`
- `EXPLAIN shows index usage in at least one scenario`

This file is where you find out whether `scenarioRegression` was actually present, skipped, or failed. Do not assume every benchmark report includes all test groups.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Check how the winner was chosen">
The PR summary should compare the frozen baseline against each candidate branch. Read that comparison before you inspect any single JSON field.

The winner should be selected because it does the best job on the same contract, not because one headline number looked better in isolation. Good winner-selection language usually includes:

- lower overall `tests.baseline.p95` than baseline
- no scenario regression ratio above the configured threshold, when scenario tests ran
- at least one selective scenario showing better pruning or fewer granules read
- caveats called out when a scenario stays flat, gets skipped, or the base query still full-scans

If another candidate looks stronger on those same measures, ask why it was not selected.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Read the saved benchmark report next">
Then open the timestamped `benchmark-*.json` file. This is the detailed evidence file for one target database.

It should tell you:

- which host and database the run hit
- the exact SQL that ran
- baseline `p50` and `p95`
- per-run query-log profiles such as `readRows`, `readBytes`, `memoryUsage`, and `durationMs`
- `EXPLAIN` output such as `indexCondition`, `selectedGranules`, `totalGranules`, and `granuleSkipPct`

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Read scenario regressions when they exist">
If `test-results.json` shows that `scenarios do not regress` ran, then open `tests.scenarioRegression`. This is where the selective scenarios usually reveal whether the optimization helped the filtered paths you care about.

What to look for:

- which scenarios improved materially
- whether any scenario crossed the configured regression threshold
- whether one scenario explains most of the win while the others stay flat
- whether the PR caveats match what the scenario data actually shows

<GuideStepper.Checkpoint title="Read EXPLAIN as its own gate">
Then look at `tests.explain`. Do not assume the unfiltered base query must stop returning `indexCondition: "true"`. In the current benchmark package, the more important question is whether at least one **selective scenario** starts pruning where the baseline did not.

Good shape:

- baseline can still full-scan
- one or more selective scenarios show a narrower `indexCondition`
- selective scenarios read fewer granules in the winner than in the baseline

Example:

```json
{
  "tests": {
    "explain": {
      "baseline": {
        "explain": {
          "indexCondition": "true",
          "granuleSkipPct": 0
        }
      },
      "category=A3": {
        "explain": {
          "indexCondition": "category in ['A3']",
          "granuleSkipPct": 75
        }
      }
    }
  }
}
```

It is possible for the baseline latency threshold to pass while the `EXPLAIN` assertion still fails. In that case, trust the failing assertion and the saved `EXPLAIN` output over the PR text.

</GuideStepper.Checkpoint>

This command uses your current local branch, so it writes the matching preview credentials into `.env.preview`.
</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Validate the preview target before you run">
Review `.env.preview` before the first run and make sure it points at the preview branch you want to test. In particular, check that `MOOSE_CLICKHOUSE_CONFIG__DB_NAME` matches that branch's preview database name.

These are the fields to check in `.env.preview`:

```bash
MOOSE_CLICKHOUSE_CONFIG__HOST=...
MOOSE_CLICKHOUSE_CONFIG__HOST_PORT=...
MOOSE_CLICKHOUSE_CONFIG__USER=...
MOOSE_CLICKHOUSE_CONFIG__PASSWORD=...
MOOSE_CLICKHOUSE_CONFIG__DB_NAME=...
MOOSE_CLICKHOUSE_CONFIG__USE_SSL=...
```

In most cases, only `MOOSE_CLICKHOUSE_CONFIG__DB_NAME` changes across branches.
</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Run the generated benchmark package">
Once `.env.preview` points at the baseline deployment, run the benchmark from inside the generated package:

```bash
cd query-benchmarks
pnpm bench
```

The package runs Vitest with the benchmark configuration and writes reports into `query-benchmarks/reports/`.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Use stdout for quick status only">
The terminal output is useful for quick checks:

- which ClickHouse host and database the benchmark connected to
- whether Vitest passed, failed, or skipped tests
- which assertion failed, if the run failed

Do not use the per-query timings printed to stdout as your main evidence. They are useful for spotting obvious anomalies, but the saved JSON reports are the source of truth for comparison.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Open test-results.json first">
After the run, open `query-benchmarks/reports/test-results.json` first. This tells you:

- whether the run succeeded overall
- which benchmark assertions passed, failed, or were skipped
- the exact failing assertion and stack location when something broke

For example, a run can fail because the `EXPLAIN` assertion did not find index pruning even if the baseline latency threshold still passed.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Open the saved benchmark report next">
Then open the timestamped `benchmark-*.json` file in `query-benchmarks/reports/`. This is where the detailed evidence lives:

- the target host and database
- the exact SQL that ran
- baseline `p50` and `p95`
- per-run query log profiles such as `readRows`, `readBytes`, `memoryUsage`, and `durationMs`
- `EXPLAIN` output such as `indexCondition` and `granuleSkipPct`

Use this file to understand why a run passed or failed.

</GuideStepper.Checkpoint>

<GuideStepper.Checkpoint title="Run the same package against the winner">
After the baseline run, switch to the winning candidate branch, refresh `.env.preview`, and run the same package again:

```bash
git checkout <winning-candidate-branch>
cd query-benchmarks
pnpm env:preview
pnpm bench
```

Compare the saved reports from both runs. The benchmark package stays the same. The checked-out branch and refreshed preview credentials determine which preview database you test.

</GuideStepper.Checkpoint>
</GuideStepper.Step>

  id="decide-whether-to-merge"
  number={3}

  summary="Make the final shipping decision after review and optional reruns."

<GuideStepper.WhatYouNeed>
- Benchmark review complete
- Optional reruns complete, if you chose to do them
</GuideStepper.WhatYouNeed>
<GuideStepper.WhatYouGet>
- A clear merge or request-changes decision
</GuideStepper.WhatYouGet>

<GuideStepper.Checkpoint title="Merge when you are satisfied">
Merge when benchmarks and optional reruns match what you want to ship. Otherwise request changes.

</GuideStepper.Checkpoint>

## Benchmark JSON quick reference

Use this when you need the current field map while reviewing the benchmark step above. Read `test-results.json` first for the verdict, then `benchmark-*.json` for the detailed evidence.

### test-results.json

```json
{
  "success": false,
  "numPassedTests": 1,
  "numFailedTests": 1,
  "numPendingTests": 1,
  "testResults": [
    {
      "assertionResults": [
        { "title": "baseline p95 under threshold", "status": "passed" },
        { "title": "scenarios do not regress", "status": "skipped" },
        {
          "title": "EXPLAIN shows index usage in at least one scenario",
          "status": "failed",
          "failureMessages": [
            "AssertionError: No scenario uses index pruning..."
          ]
        }
      ]
    }
  ]
}
```

### benchmark-\*.json

```json
{
  "timestamp": "2026-03-26T23:53:29.709Z",
  "target": {
    "host": "yey99hpcxa.clickhouse.boreal.cloud",
    "database": "514-demos-planes-perf-base-f9f0d"
  },
  "tests": {
    "baseline": {
      "sql": "SELECT ...",
      "p50": 22,
      "p95": 218,
      "profiles": [
        {
          "queryId": "standalone...",
          "readRows": 702027,
          "readBytes": 18254197,
          "memoryUsage": 49048628,
          "durationMs": 218
        }
      ]
    },
    "explain": {
      "baseline": {
        "sql": "SELECT ...",
        "explain": {
          "indexCondition": "true",
          "selectedGranules": 92,
          "totalGranules": 92,
          "granuleSkipPct": 0
        }
      }
    }
  }
}
```

`test-results.json` tells you whether the benchmark passed. `benchmark-*.json` tells you why.

| What to compare             | Where in the report                                                   | What good looks like                                        |
| --------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------- |
| Did the run pass?           | `test-results.json -> success`                                        | `true`, or a failure you can explain                        |
| Which assertion failed?     | `test-results.json -> testResults[].assertionResults[]`               | Clear pass/fail/skip for each test                          |
| Overall p95?                | `benchmark-*.json -> tests.baseline.p95`                              | Lower in winner than baseline                               |
| Scenario regressions?       | `benchmark-*.json -> tests.scenarioRegression`                        | Present only if scenario test ran; no ratio above threshold |
| Selective scenario pruning? | `benchmark-*.json -> tests.explain.<scenario>.explain.indexCondition` | At least one selective scenario is not `"true"`             |
| Granules skipped?           | `benchmark-*.json -> tests.explain.<scenario>.explain.granuleSkipPct` | Higher in winner for the selective scenario                 |
| Rows read?                  | `benchmark-*.json -> tests.baseline.profiles[0].readRows`             | Lower in winner when the contract is unchanged              |
| Memory usage?               | `benchmark-*.json -> tests.baseline.profiles[0].memoryUsage`          | Lower in winner when the contract is unchanged              |
