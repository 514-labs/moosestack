## Overview

This guide is for developers with a MooseStack application deployed on [Fiveonefour hosting](/hosting) who want to find and fix a slow ClickHouse query. It does not teach ClickHouse from scratch. Instead, it walks you through an AI-assisted workflow: your agent profiles the slow query, proposes different schema optimizations, and benchmarks each one on its own isolated preview database. The output is a pull request with the winning change and the evidence behind it.

You should be comfortable reading a ClickHouse query and reviewing a pull request. You do not need deep ClickHouse performance expertise. The benchmarks collect query metrics, `EXPLAIN` profiling, and resource usage, and your agent interprets them for you.

## How the experiment works

The workflow uses **preview branches** on [Fiveonefour hosting](/hosting) to run a controlled experiment. Each preview branch deploys to its own isolated ClickHouse database, so the only variable between runs is the schema change being tested.

1. **Freeze a baseline.** The agent pushes a baseline branch with your current schema, unchanged. Fiveonefour deploys it to a preview database that serves as the control.
2. **Deploy candidates.** Each proposed schema change gets its own branch. Fiveonefour deploys it to a separate preview database with the new layout applied.
3. **Benchmark all branches with the same test.** The agent generates a benchmark package that runs the same query against every preview database — baseline and candidates. The only difference is the underlying table layout.
4. **Compare and pick a winner.** The agent compares latency, `EXPLAIN` output, rows read, and memory usage across all branches, then opens a PR for the candidate that performed best.

Because every branch gets its own database on Fiveonefour, the comparison is clean. You are not benchmarking against shared infrastructure or a moving target. The baseline stays frozen, the candidates are isolated, and the benchmark query is the same everywhere.

The experiment produces a benchmarked winner and a migration plan you can review. It does **not** decide how to roll the change out to production. If the winning candidate needs a phased release, delayed cleanup, or a recovery plan, that planning happens after you approve the optimization.

## What the workflow is actually optimizing

ClickHouse performance usually comes down to one thing: whether the table's sorting key (its `ORDER BY` clause) matches the filter and grouping patterns your queries actually use.

In the example used to build this guide, the slow query was not fixed by rewriting SQL. It got faster because the table's sorting key was changed to match the query's filter columns. That shifted the `EXPLAIN indexes = 1` output from a full scan:

```text
Condition: true
Granules: 5921/5921
```

to a useful index condition with meaningful skipping:

```text
Condition: category in ['A3']
Granules: 6/24
Granule skip: 75%
```

That is the core idea behind this guide: improve the table structure so ClickHouse can skip irrelevant data, then confirm that query latency drops.

## Prerequisites

- A MooseStack app deployed on [Fiveonefour hosting](/hosting)
- The [`514` CLI](/hosting/cli) installed and authenticated
- Your local repository linked to the Fiveonefour project via [`514 project link`](/hosting/cli/projects/link)
- Agent skills installed via `514 agent init` (covered in the [tutorial](/guides/optimize-clickhouse-performance/tutorial))

The setup takes a few minutes. The agent workflow runs for several minutes while preview branches deploy and benchmarks execute. Budget roughly 30 minutes end to end for a first run.

If something blocks setup, see [Fiveonefour hosting to local setup](/hosting/workflow/fiveonefour-to-local-setup) and [Setup failures](/hosting/troubleshooting/setup-failures).

When you are ready for the step-by-step path, continue to the [tutorial](/guides/optimize-clickhouse-performance/tutorial).
